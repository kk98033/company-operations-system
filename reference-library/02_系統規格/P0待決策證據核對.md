## 2. 原六項決策證據與簽認結果

### P0-03 最終完工入庫觸發點

附件證據：

- 工單建檔附件有「運送」製程，但沒有描述完工、入庫或「運送必為最後一步」。

舊系統證據：

- `../extraction/ui-analysis/pb_sources/ct_subpoena/w_subp_pdcheck.srw:1687` 明確先檢查最後流程「運送」的 `delivercheck`。
- 同檔 `:1691`～`:1697` 再要求完工數量大於 0，才觸發資料轉換。
- 同檔 `:56`～`:125` 把完工數量增加到 `merchandise.finishnumber`；一般製程完成本身不會增加可出貨量。

結論：舊系統確實以「運送完成＋輸入完工量」作為完工入庫門檻。原建議並非完全照抄，而是相容舊安全邊界的重構。

公司最終決策（已簽認）：

- 保留「運送完成」作第一版預設前置條件。
- 另設有權限及稽核的「最終完工核定」命令；只有核定才寫入庫存流水。
- 運送完成可預填完工數量，但不得自動入庫。
- 未來若公司證明某類工單沒有運送流程，再以明確規則放行，不讓任意一般製程直接入庫。

確認者／日期：使用者（代表公司需求）／2026-08-08。

### P0-04 正式出貨量與備品量

附件證據：

- 報價／工單附件沒有出貨與備品規則；工單的印刷 `±量` 不能推論為出貨備品。

舊系統證據：

- `../extraction/ui-analysis/pb_sources/ct_subpoena/w_subp_delivery.srw:522`～`:540` 分開讀取並累加 `delivernumber` 與 `sparenumber`，再以兩者合計比較完工量，證明兩者都消耗可出貨數量。
- 同檔 `:475`～`:488` 的出貨小計只用正式出貨量乘單價。
- `../extraction/ui-analysis/pb_sources/ct_subp_acc/w_subp_sellprice.srw:1474`～`:1488` 另一條舊計價路徑卻以正式量加備品量乘單價，表示舊計價行為並不一致。

結論：正式量、備品量分欄且兩者都扣庫存是可證明的舊規則；備品是否計價不能只靠舊程式唯一決定。

公司最終決策（已簽認）：

- 正式出貨量與備品量永久分欄。
- `實際扣庫量＝正式出貨量＋備品量`。
- 出貨單同時顯示正式量、備品量與實際交付總量。

備品計價採 A；下表保留當時比較證據：

| 選項 | 規則 | 影響 |
|---|---|---|
| A（已採用） | 正式出貨量為預設計價基礎；備品只有在計價明細明確填入可請款數量／單價時才收費 | 避免免費備品被靜默收費，並保留實際交付量 |
| B | 正式出貨量＋備品量預設全數計價；免費備品需明確設為 0 | 接近舊計價畫面路徑，但有誤收風險 |
| C | 每筆出貨都必須人工明確指定備品是否計價 | 最明確，但增加每筆操作成本 |

確認者／日期：使用者（代表公司需求）／2026-08-08。

Import 注意：舊出貨程式雖計算累計正式量與備品量，但沒有可靠地把區域變數寫回 `merchandise` 累計欄；舊 `merchandise` 不能單獨當成正確庫存餘額，必須由完工與 `subp_sale2` 出貨歷史重建並產生差異報告。

### P0-05 超量出貨／負庫存

附件證據：

- Gmail 附件沒有超量出貨、負庫存或例外權限規則。

舊系統證據：

- `../extraction/ui-analysis/pb_sources/ct_subpoena/w_subp_delivery.srw:510`～`:543` 先保存出貨，再比較累計正式量加備品量。
- 當累計量大於或等於完工量時，舊程式只刪除待出貨列；沒有找到「大於完工量就拒絕」的可靠檢查。因此舊系統不能證明有禁止超量的限制，反而可能把超量隱藏成沒有待出貨資料。

原建議：

- 第一版在資料庫交易內禁止任何造成負庫存的正式出貨或備品扣除。
- 不提供一般操作員的超量例外按鈕。
- 若公司日後證明有「先出貨、後補完工」流程，再另立 ADR、核准權限、原因與上限；不可預先留一條無明確規則的後門。

使用者提出的便利性問題：舊使用者可能沒有先登完工庫存的習慣，因此只提供一般阻擋會增加操作摩擦。

公司最終決策（已簽認）：

- 不允許直接負庫存，也不提供 stock override。
- 只有系統已有對應工單的有效「運送完成」事件，且操作者具 `shipment.complete_and_confirm` 專用權限時，才可使用「補登完工並出貨」。
- 操作者輸入真實完工量及必填原因；同一資料庫交易先建立獨立最終完工紀錄與正向庫存流水，再建立出貨與負向流水。多明細任一步失敗即整張回滾。
- 兩個業務事件保留各自語意，並以 correlation ID、idempotency key、並行鎖及 audit 串接；交易後庫存不可為負。
- 補登量可反映本次實際整批完工量，不只限短缺量但不得小於短缺量；累計完工超過訂購量時必須警告、確認並記錄原因。這只放行實際完工量，正式出貨與備品仍依 ADR-016 分欄，不放行任意正式超交。
- 取消出貨不自動沖銷真實完工；錯誤完工另走完工沖銷。Import 不為了補平舊餘額合成這類事件。

確認者／日期：使用者（代表公司需求）／2026-08-09。詳見 ADR-019。

### P0-06 客戶稅額與取整

附件證據：

- 新報價／工單附件只有單價兩位小數、版費及刀模費，沒有未稅小計、稅率、稅額、含稅總額或取整欄位。因此報價與工單頁不可自行增加稅額區。

舊系統證據：

- `../extraction/ui-analysis/pb_sources/CT_CUST/d_detail_cust.srd:20`～`:21`、`:50`～`:54` 有客戶層級的「稅額請款」與「對帳單每筆合計」設定。
- `../extraction/ui-analysis/pb_sources/ct_subp_acc/w_subp_recbell.srw:270`～`:278` 會依 `cust.C_TAX` 決定對帳單是否顯示稅額。
- `../extraction/ui-analysis/pb_sources/ct_subp_acc/d_subp_recbell1.srd:47`、`:68`～`:70` 先把每筆金額取整，再以固定 5% 算稅並加總。
- 舊報價 `../extraction/ui-analysis/pb_sources/Ct_bill/d_replay1_det.srd:28`～`:29` 另有「本報價單：含稅」勾選。

結論：稅額並非推測，舊系統確實有；但公司新附件未顯示或要求稅額欄位。不可據此自行在報價／工單增加稅額 UI，也不可反向推論公司已廢除請款稅務。舊資料欄位的實際匯出值仍有異常，不能直接當可靠設定匯入正式表。

公司最終決策（已簽認）：

- 新版報價與工單不顯示或自動計算稅額。
- 請款／對帳保留「是否計稅」能力但預設關閉；只有明確啟用時才計算，稅率與取整規則保存文件快照，不硬編成永遠 5%。
- 舊稅額、取整欄及歷史總額仍依 P0-10 只讀保存並可核對。

確認者／日期：使用者（代表公司需求）／2026-08-08。

### P0-07 請款單與對帳單格式

附件證據：

- 目前公司提供的是報價單與工單，不是請款單或對帳單；報價單不能代替此項格式確認。

舊系統證據：

- `../extraction/ui-analysis/pb_sources/ct_subp_acc/w_subp_recbell.srw` 是單一「請款對帳作業」。
- `../extraction/ui-analysis/pb_sources/CT_ACC/d_recbell1.srd:41` 的列印抬頭是「應收帳款對帳單（一般類）」。目前沒有找到舊系統同時存在兩種獨立請款／對帳模板的可靠證據。

公司最終決策（已簽認）：

- 第一版只建立一種正式「對帳單」文件與列印模板。
- 「待請款／已請款」是流程狀態，不另外建立內容重複的請款單模板。
- 公司日後提供不同請款格式時，再共用同一帳款資料新增第二種模板，不複製帳款資料表。

確認者／日期：使用者（代表公司需求）／2026-08-08。

舊系統證據：

使用者已給方向：新版使用英文前綴，且舊版單號必須能原樣觀看。

公司最終決策（已簽認）：

| 文件 | 新版顯示號 |
|---|---|
| 報價 | `QUO-YYYYMMDD-SS` |
| 案件 | `CASE-YYYYMMDD-SSS` |
| 工單 | `WO-YYYYMMDD-SSS` |
| 出貨 | `SHP-YYYYMM-SSS` |
| 計價 | `PRC-YYYYMMDD-SSS` |
| 對帳 | `STM-YYYYMM-SSS` |
| 收款 | `RCT-YYYYMMDD-SSS` |

共同規則：

- 資料庫內部主鍵使用不可變 ID，不把顯示單號當關聯主鍵。
- 新單號在公司與文件類型內唯一；資料庫交易內配發。
- 日期修改不改已配發單號；作廢後不回收；另存新檔一定取得新號。
- 舊資料保存 `legacy_document_number` 與來源表／主鍵，畫面標示「舊系統」，可用新內部 ID 或舊號搜尋；不替舊資料補英文前綴或覆寫原號。

確認者／日期：使用者（代表公司需求）／2026-08-08。

2. 打樣
