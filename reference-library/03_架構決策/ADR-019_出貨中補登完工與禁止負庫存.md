# ADR-019：出貨中補登完工與禁止負庫存

- 狀態：Accepted
- 日期：2026-08-09
- 決策者：使用者（代表公司需求）

## 背景

舊系統沒有可靠的超量出貨阻擋，且公司人員可能沒有先登記完工庫存的習慣。新版若只在庫存不足時拒絕，會讓原有出貨流程卡住；若直接允許負庫存，又會隱藏未登完工或數量錯誤。

## 決策

1. 一般出貨永遠不得造成負庫存，也不建立 stock override。
2. 出貨不足時，只有工單已存在目前有效、未沖銷且製程未重開的「運送完成」事件，且操作者具 `shipment.complete_and_confirm` 專用 capability，才可啟動「補登完工並出貨」。事件必須屬於同公司、同工單及目前有效的運送製程，工單也不得為禁止異動狀態。
3. 操作者必須輸入本次真實完工量及原因。系統在同一資料庫交易依序建立：
   - 獨立 `final_completion_entry` 與正向庫存流水。
   - 出貨主明細與負向庫存流水。
4. 完工與出貨是兩個獨立、可沖銷及可稽核的業務事件，以 correlation ID 串接；不得偷偷改餘額或把完工包裝成超量核准。
5. 整張多明細出貨 atomic；任一步失敗全部回滾。命令必須有 idempotency key、並行鎖與交易後非負驗證。
6. 完工量可填本次實際整批完工量，不只限短缺量，但不得小於本次短缺量。累計完工超過工單訂購量時，UI 與 API 都必須警告並要求原因，audit 保存確認者與數值。
7. 上一項只允許「實際完工量」超過訂購量，不表示正式出貨量可任意超過尚未正式交付量；超出但屬備品者必須記在 `spare_quantity`，其他超交規則另行定案。
8. 取消出貨只沖銷出貨事件，不自動沖銷真實完工；完工有誤時另走完工沖銷，且有效出貨未先沖銷前不得沖銷其關聯完工。
9. 舊資料 Import 保留來源事實及差異，不為了補平歷史餘額合成「出貨中補登完工」事件。

## 結果

- 保留舊使用者在出貨當下補登真實完工的便利性。
- 庫存流水仍可重建、可核對，且任何時間都不以負庫存作正常流程。
- Phase 1 只先定義 capability；實際角色對 capability 的 mapping 由 P1-02 確認。

## 必要驗收

- 無有效運送完成事件、無專用權限、未填原因或完工量不合法時拒絕。
- 正向完工與負向出貨同交易成功，任一步失敗均不留部分資料。
- 重送、並行出貨、多明細其中一筆不足及流水競爭都不重複、不超扣、不負庫存。
- 超過訂購量時需二次確認與原因；取消出貨後完工仍存在。
