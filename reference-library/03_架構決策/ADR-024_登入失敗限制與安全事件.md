# ADR-024：登入失敗限制與安全事件

> 日期：2026-08-12
> 狀態：Accepted

## 背景

登入 API 必須限制重複猜密碼，但不能因狀態碼、資料表或事件內容洩漏帳號是否存在。系統未來可部署給 B 公司，因此 A、B 公司的登入限制也不能互相影響。

## 決策

1. 以 `HMAC-SHA256(AUTH_SECURITY_HMAC_KEY, company id + normalized login bucket)` 產生 64 字元指紋；資料庫不保存登入輸入、密碼或 IP。
2. 同一公司／帳號 bucket 在 15 分鐘內第五次失敗時限制 15 分鐘；前四次回通用 401，第五次起回固定 429 與整數 `Retry-After`。
3. 已知、未知、停用、鎖定、錯公司及錯密碼皆使用相同 bucket 規則與公開文案；未達限制時仍執行一次 Argon2 verify。
4. 成功登入會在建立 Session 的同一交易刪除既有失敗狀態，並留下不含原始帳號的成功安全事件。
5. 同一 bucket 以 PostgreSQL transaction advisory lock 序列化，避免並行失敗遺失計數。`login_security_events` 由 trigger 禁止一般 UPDATE／DELETE。
6. `AUTH_SECURITY_HMAC_KEY` 必須和 `CSRF_HMAC_KEY` 不同。本機只放 gitignored `.env`；正式環境由 owner-only 環境檔或 Secret Manager 在 runtime 注入，不進 Git、React、image 或 log。

## 影響

- B 公司使用不同 organization id，因此即使使用者代號相同也有不同指紋；獨立部署時另使用不同 Secret 與資料庫。
- 輪替 `AUTH_SECURITY_HMAC_KEY` 會改變指紋；部署時應先清除短期 throttle state，舊 append-only 事件保留但不再和新指紋聚合。
- 本 Slice 不信任 proxy header，也不做 IP 全域限流。正式公開網路前若需來源限流，必須先定義可信 proxy 邊界，不能直接信任 `X-Forwarded-For`。

## 回復方式

可降回 `0006_audit_foundation` 移除兩張登入安全表；不得以停用限流作為正常故障處理。若策略需調整，先以測試更新門檻、時間窗與公開錯誤契約。
