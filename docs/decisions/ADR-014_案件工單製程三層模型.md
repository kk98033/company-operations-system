# ADR-014：案件、工單、製程任務三層模型

- 狀態：Accepted
- 日期：2026-08-08
- 決策者：使用者（代表公司需求）
- 對應：P0-01、P0-02、CASE-001～CASE-005、QUO-006

## 1. 背景

舊系統的報價使用 `b_replay1` 主檔與 `b_replay2` 多筆明細；製程傳票則使用獨立 `subpoena`，每筆只有一組工作名稱與訂購數量。抽出的 PowerBuilder 程式沒有找到報價自動轉工單或報價與工單的可靠外鍵。下游製程、庫存與出貨都以單張傳票為追蹤單位。

公司希望保留一張報價可含多項品項，又能把同一客戶訂單集中管理，因此需要在報價與工單間增加不干擾生產追蹤的分組層。

## 2. 決策

1. 採用「案件 → 工單 → 製程任務」三層模型。
2. `production_cases` 是同一客戶訂單或同一張報價的管理容器，保存客戶、來源報價、客戶訂單號、案件交期、摘要狀態與快照。
3. 一個案件包含一張或多張工單；一張工單只能屬於一個案件。
4. 一張工單只對應一個主要品項，獨立保存數量、材料、印刷、價格、交期、附件、完工、庫存及出貨關係。
5. 報價轉換時，使用者可勾選多筆明細；系統在同一交易建立一個案件，且每筆選中的報價明細各建立一張子工單。不同報價明細不合併成同一張工單。
6. 直接建立工單時，系統自動建立一個單工單案件，不要求操作員先多做一個案件步驟；日後可在符合權限與客戶一致性規則下加入其他工單。
7. 製程任務隸屬工單；案件只彙總子工單狀態，不直接保存可人工覆寫的製程完成、庫存或出貨總數。
8. 報價轉換命令必須具備 idempotency 保護。報價日後修改不得覆蓋既有案件或工單；重新轉換需明確顯示既有關係並由規則允許。

## 3. 狀態與完成規則

- 案件狀態至少能區分草稿、進行中、部分完成、全部完成、作廢。
- 案件的進度摘要由有效子工單推導；不能因一張工單完成就把整個案件標為全部完成。
- 作廢案件不得直接刪除子工單；每張已建立工單仍依自己的作廢／沖銷規則處理並保留稽核。
- 案件本身不產生庫存；只有工單的最終完工核定可寫入庫存流水。

## 4. 舊資料移轉

- 舊工單沒有可靠案件鍵，每張舊工單先建立一個 `legacy_single_work_order` 案件，確保不猜測分組。
- 只有取得可驗證的共同訂單／報價關係並經公司抽樣簽認後，才可把多張舊工單合併到同一案件。
- `b_replay1`／`b_replay2` 匯入新版報價主檔／明細，但沒有證據時不得臆造它與舊 `subpoena` 的轉換關係。

## 5. 驗收條件

- 一張三明細報價可在一次操作建立一個案件與三張各自有來源明細的工單。
- 同一轉換請求重送不重複建立案件或工單。
- 直接建立單張工單時自動得到一個案件，操作員不需先填第二張表單。
- 任一子工單延遲、完成、作廢或部分出貨時，案件摘要正確且不改寫其他工單。
- 工單、完工、庫存、出貨與計價仍能逐張追溯；案件頁可集中查看所有子工單。

## 6. 重新評估條件

只有公司提供必須在同一張生產工單中同時保存多個獨立品項、各自材料／製程／數量的實際案例時，才重新評估多品項工單；一般的同訂單多品項仍以一案件多工單處理。
