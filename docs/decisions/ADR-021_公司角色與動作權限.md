# ADR-021：公司角色與動作權限

- 狀態：Accepted
- 日期：2026-08-09
- 決策者：開發端，依既定架構、P1-02 未決邊界與 PostgreSQL 驗證
- 相關 Slice：Phase 1 Slice 1.6～1.7

## 1. 背景

系統需要讓同一使用者加入不同公司，並依公司取得不同角色。公司尚未簽認管理員、業務、生產、會計與唯讀角色的完整 capability mapping，因此本 Slice 必須先完成安全且可擴充的授權引擎，不能把候選矩陣硬寫成正式規則。

## 2. 決策

1. `permissions` 是全域動作目錄，代碼採正規化小寫分段，例如 `settings.manage`；不接受角色名稱、萬用字元或隱式管理員捷徑。
2. `roles` 屬於單一 organization；`role_permissions` 是純 allow 集合。沒有規則即 deny，不建立難以追蹤的 deny override。
3. `organization_member_roles` 同時保存 organization，並以公司＋成員及公司＋角色兩組複合外鍵在 PostgreSQL 層拒絕跨公司指派。
4. 後端 `require_capability()` 是正式安全邊界。前端 `CapabilityGate` 只改善操作體驗，不能取代 API 的 403。
5. current Session 回傳目前公司仍有效的精確 capability。role、permission、membership、user 或 organization 任一停用時不再授權。
6. Slice 1.6 migration 不加入正式角色 seed。P1-02 簽認前，allow／deny 測試只建立清楚標示 synthetic 的角色與 capability。

## 3. 結果

- 使用者可在不同公司擁有不同角色，且 DB、service 與 UI 使用同一 capability 語意。
- 角色名稱可調整，不需在每個業務 API 搜尋並修改 `admin` 判斷。
- 未簽認的公司角色矩陣不會污染 schema 或 migration；後續只需新增資料與驗收 fixture。
- Slice 1.7 仍須為所有業務 repository／service 加入 organization scope；本 ADR 不等於已完成所有跨公司資料隔離。

## 4. 必要驗收

- 同公司 grant 允許、缺 grant 拒絕；停用 role 或 permission 立即拒絕。
- 跨公司 role assignment 由真 PostgreSQL 外鍵拒絕。
- API 未授權回穩定 403；UI 不顯示未授權操作，且不能只靠 UI 保護。
- OpenAPI Session schema 與 generated client 都包含排序穩定的 capability 清單。
- P1-02 簽認前 production migration／seed 不含候選業務 mapping。
