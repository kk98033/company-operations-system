# 測試與驗收計畫

> 目標：每完成一小部分立即驗證，不把數量、金額及資料關聯問題累積到專案最後。

## 1. 測試層次

| 層次 | 工具 | 驗證內容 |
|---|---|---|
| 後端單元 | Pytest | Decimal、狀態、數量、權限、mapping |
| 後端整合 | Pytest＋真實 PostgreSQL | migration、constraint、交易、鎖、並行 |
| API | FastAPI TestClient／HTTP client | schema、錯誤碼、session、CSRF、公司 scope |
| 前端單元 | Vitest | formatter、schema、元件行為 |
| 前端整合 | React Testing Library＋MSW 或測試 API | 表單、列表、錯誤、權限及狀態 |
| 前端無障礙 | axe-core＋React Testing Library＋實際瀏覽器 | WCAG A／AA、ARIA、單一 H1、鍵盤焦點、尺寸與色彩人工基線 |
| E2E | Playwright | 瀏覽器端到端主流程與角色 |
| 列印 | Playwright screenshot／PDF 基線＋實體印表機 | A4 方向、分頁、字型、黑白可讀性 |
| 移轉 | Pytest＋核對 SQL | 筆數、關聯、總量、金額、亂碼及重跑 |
| 備份／還原 | 自動腳本＋E2E smoke | 從乾淨環境恢復完整系統 |
| UAT | 公司操作腳本 | 真實工作方式、文件及例外流程 |

## 2. 每個 Slice 的最小驗證集合

### 純文件／設定 Slice

- 文件連結檢查。
- 必要章節與 README 進度欄位檢查。
- 決策、架構、計畫與需求矩陣一致性人工檢查。

### Migration Slice

- 空資料庫 upgrade。
- 有前一版本資料的 upgrade。
- downgrade（若安全）或已記錄前進修復策略。
- constraint 正常與失敗案例。
- migration 後模型與 OpenAPI 測試。

### API Slice

- 成功案例。
- schema／必填錯誤。
- 未登入。
- 無權限。
- 跨公司。
- 不存在資料。
- 錯誤狀態轉換。
- version conflict／並行，適用時。

### UI Slice

- loading。
- 正常資料。
- 空資料。
- 驗證錯誤。
- API 業務錯誤。
- 無權限。
- 鍵盤操作及焦點。
- `npm run test:a11y` 無 axe 違規；新增路由／互動狀態同步加入掃描。
- 主模組每條 URL 都可直接進入、只有一個 H1、側欄 active 正確，且明確標示假資料／未連 API。
- 客戶、報價、案件、工單、生產、庫存、出貨、計價、請款／對帳到收款可逐站操作，不只測單一頁 render。
- 1920×1080、1366×768、1280×720 與窄視窗不破版。
- 色彩對比、焦點可見性及螢幕閱讀脈絡由實際瀏覽器人工複核，不以 JSDOM 結果取代。

### 高風險業務 Slice

- 單元規則。
- 真實 PostgreSQL transaction。
- 並行請求。
- E2E 正常流程。
- 作廢／沖銷。
- audit log。

## 3. 固定測試資料

測試 seed 只使用虛構資料：

- 公司：測試印刷股份有限公司。
- 管理員、一般操作員、生產、會計、唯讀帳號。
- 客戶 A：新對帳單預設不計稅，另一筆明確啟用虛擬稅率與逐筆取整的對帳案例。
- 客戶 B：帶有只讀 legacy 稅務／取整值，驗證不會自動污染新對帳單預設。
- 供應商、協力廠、面紙、底紙、浪紙及標準製程。
- 報價：一張單明細、一張多明細。
- 工單：直接建立、報價轉入、新版、舊版。
- 數量案例：完工 600＋400，出貨 500＋備品 10，再出貨 300。
- 計價案例：免費備品不自動計價；另一筆明確輸入備品可請款數量與單價。
- 帳款案例：一張對帳單部分收款、一筆收款分配兩張對帳單。

Seed 必須可重跑，且不得使用真實客戶名稱、電話、地址或正式文件圖片。

### 附件契約回歸資料

Phase 3／4 的欄位與列印測試必須以 `docs/Gmail附件需求逐項對照.md` 為入口，分開使用四種證據：

| 證據 | 測試責任 |
|---|---|
| 建檔空白稿 | 欄位存在、順序、分區、RWD 與鍵盤操作 |
| 註解稿 | 自動帶入、格式、兩位小數、控制元件、容量及主檔來源 |
| 範例稿 | 以等價虛構資料建立 UAT fixture，驗證完整輸入／讀回；不得複製真實公司資料作 seed |
| 列印稿 | A4 方向、欄位完整、按鈕隱藏、圖片／分頁與文件快照 |

- 報價至少測單明細、多明細動態序號、明細附註／文件備註、另存新檔與 A4 橫向。
- 工單建檔至少測三種備紙 typed 欄位、正反面 CMYK／特別色、13 道製程及專屬欄、150 字備註與圖片。列印另依公司稿測 A4 直向與固定 9 道製程；若公司簽認擴充完整 13 道，必須新增對應列印回歸測試。
- P0-01／P0-02 已定案為一案件多張單品工單；P0-09 亦已依 ADR-018 定案，附件舊範例只用來核對 legacy 顯示，不覆寫新格式。

## 4. 必測端到端案例

### E2E-01 直接建立工單

```text
登入
→ 選擇客戶
→ 直接建立工單
→ 填材料、印刷、製程、附件
→ 確認及列印
→ 查詢找到工單
```

預期：沒有報價也能完成；快照與來源正確。

### E2E-02 報價轉工單

```text
建立報價
→ 加入兩筆明細
→ A4 橫向預覽
→ 確認
→ 勾選兩筆明細建立一個案件
→ 系統建立兩張各自保留來源的子工單
→ 逐張調整並確認工單
```

預期：一個案件含兩張獨立工單；轉換重送不重複建立，報價後續變更不覆蓋案件或工單。

### E2E-03 部分完工與多次出貨

```text
工單數量 1,000
→ 一般製程完成（庫存仍 0）
→ 運送製程完成（庫存仍 0）
→ 最終完工 600（庫存 600）
→ 再完工 400（庫存 1,000）
→ 出貨 500＋備品 10（庫存 490）
→ 再出貨 300（庫存 190）
```

### E2E-04 出貨沖銷

取消第二次出貨後預期庫存回到 490；原出貨與負向流水仍存在，另有反向流水。

### E2E-05 並行出貨

庫存 100，兩個 session 同時各出貨 80；最多只有一個成功，庫存不得為負。

### E2E-06 防重複計價

兩個 session 同時計價同一出貨明細；最多一個成功，失敗者看到明確訊息。

### E2E-07 計價與價格記憶

建立基礎計價、加入版費與刀模費、更新預設價格；下一筆同客戶品項能看到來源、日期與建議，但不自動覆蓋。

### E2E-08 請款與部分收款

建立唯一對帳單，先驗證預設稅額為 0，再用明確啟用的另一案例驗證稅率及取整快照。對帳單進入已請款狀態後，登記部分收款再登記尾款；狀態依序為已請款、部分收款、已收款。

### E2E-09 權限

- 生產角色不能看收款。
- 會計不能修改已確認工單製程規格，除非權限矩陣允許。
- 一般操作員不能超量出貨、沖銷收款或管理使用者。

### E2E-10 跨公司

A 公司使用者即使猜到 B 公司 UUID，也不能開頁面、下載附件、修改、匯出或透過搜尋看到名稱。

### E2E-11 新舊單號

- 七類新文件都使用 ADR-018 格式，同時配號不重複。
- 不同公司各自配號，公司 A 的流水不佔用公司 B 的號碼。
- 日流水跨日、月流水跨月重置；各文件類型互不佔用。
- 日期修改不重編號，作廢不重用，另存新檔取得新號。
- 舊號不加前綴，畫面標示舊系統並可搜尋到新資料列。
- `SS` 第 100 筆／`SSS` 第 1,000 筆在同日或同月依 ADR-018 明確拒絕並通知管理者，不靜默擴位、重用或重號。

### P0-05 候選回歸測試（未簽認，不實作）

若公司採修正建議，必測：一般出貨庫存不足時拒絕；專用權限者可在運送完成後明確輸入實際完工量與原因；完工正向流水與出貨負向流水在同一交易完成；任一步失敗全部 rollback；重送不重複建立；並行後餘額不為負；出貨取消不自動沖銷真實完工。

## 5. 金額驗證

開工前由公司提供至少三張實際但可安全處理的對帳案例，轉成去識別測試 fixture：

1. 不含稅、無取整。
2. 含稅或稅額請款。
3. 每筆小計取整與總額取整有差異。

每個案例固定保存：

- 原始明細。
- 計算中間值。
- 預期小計。
- 預期調整。
- 預期稅額。
- 預期總額。

禁止只測最終總額而沒有中間值，否則錯誤可能互相抵銷。

## 6. 列印驗收

### 自動檢查

- 紙張尺寸及方向。
- 元件不超出 page box。
- 操作按鈕及導覽不出現在 print mode。
- 多明細正確分頁。
- 頁首／頁尾不遮住明細。
- 黑白 screenshot 對比可讀。
- 固定 fixture 的視覺差異在審核範圍內。

### 實體印表機

每一種正式文件至少在公司實際印表機測試：

- 100% 縮放。
- 瀏覽器預設頁首頁尾關閉。
- 中文字型正確。
- 框線、欄位及圖片不截斷。
- 黑白列印不依賴顏色辨識。

簽認文件：報價、工單、出貨單、對帳單（請款為狀態）。

## 7. 效能與容量基線

第一版不追求大量壓測，但要以代表資料量驗證：

- 兩位使用者同時登入及操作。
- 客戶至少 221 筆以上。
- 工單、製程、出貨及計價建立數年代表資料。
- 常用列表第一頁有分頁且不抓全部明細。
- 關鍵字搜尋有 query plan 紀錄。
- 備份執行時核心操作仍可接受。

效能門檻在 Phase 9 依測試主機量測後填入，不在沒有證據時硬寫不切實際數字。

## 8. 備份與還原驗收

至少每季及正式切換前：

1. 建立全新 VM 或乾淨本機環境。
2. 只使用 README、Git remote／bundle、備份檔與 Secret 還原說明。
3. 還原 PostgreSQL。
4. 還原附件及文件快照。
5. 執行 migration。
6. 登入並跑 E2E smoke。
7. 抽樣開啟歷史附件與列印文件。
8. 建立測試出貨、計價及收款。
9. 記錄開始／完成時間、失敗點及 RPO／RTO。

## 9. UAT 簽認

每個核心模組由實際使用者完成：

| 模組 | 建議簽認者 | 必看內容 |
|---|---|---|
| 客戶、報價、工單 | 業務／主要操作員 | 欄位、查詢、列印、另存新檔 |
| 製程、完工、庫存 | 生產／主要操作員 | 狀態、最終核定、數量 |
| 出貨 | 出貨操作員 | 部分、多次、備品、沖銷、列印 |
| 計價 | 計價操作員 | 來源、防重複、歷史價格 |
| 請款、收款 | 會計 | 稅額、取整、文件、餘額 |
| 權限與稽核 | 管理者 | 角色、敏感操作、追溯 |
| 備份與還原 | 系統維護者＋公司負責人 | 可還原、資產所有權 |

## 10. 測試證據

每個 Slice 的進度紀錄至少寫：

- 測試日期。
- 環境與 commit。
- 執行命令。
- 成功／失敗數。
- 人工驗證步驟。
- screenshot／報告位置，若適用。
- 未解問題。

不得只寫「測試 OK」而沒有命令與範圍。
