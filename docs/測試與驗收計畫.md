# 測試與驗收計畫

> 目標：每完成一小部分立即驗證，不把數量、金額及資料關聯問題累積到專案最後。

## 1. 測試層次

| 層次 | 工具 | 驗證內容 |
|---|---|---|
| 後端單元 | Pytest | Decimal、狀態、數量、權限、mapping |
| 後端整合 | Pytest＋真實 PostgreSQL | migration、constraint、交易、鎖、並行 |
| API | FastAPI TestClient／HTTP client | schema、錯誤碼、session、CSRF、公司 scope |
| 前端單元 | Vitest | formatter、schema、元件行為 |
| 前端整合 | React Testing Library＋MSW 或測試 API | 表單、列表、錯誤、權限及狀態 |
| 前端無障礙 | axe-core＋React Testing Library＋實際瀏覽器 | WCAG A／AA、ARIA、單一 H1、鍵盤焦點、尺寸與色彩人工基線 |
| E2E | Playwright | 瀏覽器端到端主流程與角色 |
| 列印 | Playwright screenshot／PDF 基線＋實體印表機 | A4 方向、分頁、字型、黑白可讀性 |
| 移轉 | Pytest＋核對 SQL | 筆數、關聯、總量、金額、亂碼及重跑 |
| 備份／還原 | 自動腳本＋E2E smoke | 從乾淨環境恢復完整系統 |
| UAT | 公司操作腳本 | 真實工作方式、文件及例外流程 |

## 2. 每個 Slice 的最小驗證集合

### 純文件／設定 Slice

- 文件連結檢查。
- 必要章節與 README 進度欄位檢查。
- 決策、架構、計畫與需求矩陣一致性人工檢查。

### Migration Slice

- 空資料庫 upgrade。
- 有前一版本資料的 upgrade。
- downgrade（若安全）或已記錄前進修復策略。
- constraint 正常與失敗案例。
- migration 後模型與 OpenAPI 測試。

Slice 1.1 identity migration 另固定驗證：使用者代號 trim／不分大小寫唯一；同一使用者可加入不同公司但不可重複加入同公司；不存在的公司／使用者／成員外鍵拒絕；session 只存 64 字元 digest、生命週期時間合法且父資料受 `RESTRICT`；從含既有 Import row 的 `0003` 升降後資料仍存在。

Slice 1.3 auth API 另固定驗證：登入名稱 trim／不分大小寫、明確 organization membership、不同登入產生不同 token、固定 8 小時到期、raw token 只在當時的成功 response 出現且 DB 只存 SHA-256 digest、`last_login_at` 與 Session 同交易；未知帳號／錯密碼／錯公司／停用或鎖定 user／停用 organization／停用 membership 必須回逐 byte 相同 401，未知帳號仍執行 Argon2 dummy verify。Resolver 必須拒絕到期、撤銷及任一身分邊界停用的 Session；登出首次、重跑、過期及未知格式正確 token 都維持相同 204，第一次 `revoked_at` 不可被重寫。Slice 1.3 checkpoint 的 OpenAPI 曾以 `SessionBearer` 驗證過渡 transport；Slice 1.4 必須另證明該契約已完全移除，不能把歷史 checkpoint 當現行瀏覽器規格。

Slice 1.4 瀏覽器 Session 另固定驗證：登入成功後 raw token 只存在 host-only HttpOnly Cookie，JSON／OpenAPI／generated client／DB 不得保存 raw 值；SameSite=Strict、兩個 Cookie path、production Secure、無持久 Max-Age／Expires 都需逐項檢查。CSRF 必須是伺服器 HMAC 簽章且綁定 Session digest的 signed double-submit；只相等但偽造、跨 Session 搭配、缺 Cookie／Header都必須拒絕。登入／登出以單一設定來源 exact-match Origin，缺 Origin 才以同源 Referer fallback，missing、`null`、foreign、suffix spoof及多值都 fail closed且不得異動 Session。登出須先撤銷再清 Cookie，DB 失敗不得清除；無／畸形 Cookie則維持冪等 204。OpenAPI 只能有 `SessionCookie`，不可殘留 Bearer、Authorization、`session_token` 或 `token_type`；正式目前使用者 endpoint 與 React UI 不得提前出現。

Slice 1.5 登入 UI 另固定驗證：`GET /api/v1/auth/session` 只接受 HttpOnly Cookie 並回使用者／公司／到期時間，不回 token 或 CSRF；React 未登入訪問受保護路由導到 `/login`，有效 Cookie 在重新整理後恢復原工作區，過期／401 回登入頁，網路錯誤則不偽裝成未登入。登入必須送出部署的公開 organization ID、使用者代號與密碼，成功只寫 TanStack Query Session cache；登出由 readable CSRF Cookie 建立 `X-CSRF-Token`，204 後清除 cache 並回登入頁。測試及產品程式搜尋不得出現 `localStorage` 登入旗標、密碼保存或 raw Session token；登入頁納入 axe WCAG A／AA 與 RWD 人工驗收。

Slice 1.8 稽核另固定驗證：migration 從 0005 升級、完整升降與 autogenerate drift；actor organization／membership／user 複合外鍵拒絕跨公司組合；業務異動與 audit 同 transaction commit，強制失敗時一起 rollback；PostgreSQL 拒絕 audit UPDATE／DELETE。sanitizer 必須遞迴遮罩密碼／hash、Cookie、CSRF、Session、Token、Secret、私鑰、API key、bytes／檔案內容並限制大小，唯讀 API response 再遮罩一次。Request ID 每次由伺服器產生、忽略 client header，成功／錯誤 response 與安全 log 使用同一 ID。`GET /audit-logs` 需要 active Cookie Session＋`audit.read`，分頁上限 100，A 公司不得看到 B 公司紀錄；React 頁固定測 loading、空資料、錯誤、403、不發未授權 request、RWD 及 axe。

Slice 1.9 登入安全另固定驗證：migration 從 0006 升級、完整升降與 autogenerate drift；同一公司／登入 bucket 前四次失敗使用通用 401，第五次起固定 429＋正整數 `Retry-After`，15 分鐘限制時間內不再執行密碼驗證。已知、未知、停用、鎖定、錯公司與錯密碼使用相同門檻；成功登入會在 Session 建立交易內刪除失敗狀態。指紋必須含 organization ID 且不含 raw 帳號、密碼或 IP，A／B 公司同名帳號不可共用計數；security event 的 UPDATE／DELETE 必須由 PostgreSQL 拒絕。並行同 bucket 不得遺失計數；HMAC key 缺少、弱值、沿用範例或與 CSRF key 相同時 fail-fast，錯誤不得回顯 key。

## 3. 固定測試資料

測試 seed 只使用虛構資料：

- 公司：測試印刷股份有限公司。
- 管理員、一般操作員、生產、會計、唯讀帳號。
- 客戶 A：新對帳單預設不計稅，另一筆明確啟用虛擬稅率與逐筆取整的對帳案例。
- 客戶 B：帶有只讀 legacy 稅務／取整值，驗證不會自動污染新對帳單預設。
- 供應商、協力廠、面紙、底紙、浪紙及標準製程。
- 報價：一張單明細、一張多明細。
- 工單：直接建立、報價轉入、新版、舊版。
- 數量案例：完工 600＋400，出貨 500＋備品 10，再出貨 300。
- 計價案例：免費備品不自動計價；另一筆明確輸入備品可請款數量與單價。
- 帳款案例：一張對帳單部分收款、一筆收款分配兩張對帳單。

Seed 必須可重跑，且不得使用真實客戶名稱、電話、地址或正式文件圖片。

Slice 1.2 的 identity seed 固定只建立一間明示虛構公司、兩個虛構帳號與兩筆 membership；「管理員／操作員」在 Slice 1.6 前只是名稱，不代表權限。兩個測試密碼由 runtime 產生或隱藏輸入，不寫進 fixture、Git 或輸出；資料庫只存可驗證的 Argon2id hash。首次、重跑、改密碼、固定 ID、正規化 login、部分缺 membership、production fail-fast、CLI 安全輸出與整批 rollback 都必須用隔離 PostgreSQL／spy 驗證。

Slice 2.1 的公司 profile 必須以兩間虛構公司驗證：A 公司的讀取、更新與 audit 不得改動或洩漏 B；無 `settings.manage`、缺 signed CSRF 與 stale `updated_at` 分別回固定拒絕。Logo metadata 必須全有或全無，object key 不出現在 API response／React；桌面與 390px 實際驗證即時抬頭預覽、存檔與無整頁水平溢位。

Slice 2.2 的公司設定必須驗證：既有公司升級 `0009` 後自動取得一筆預設關閉設定；關閉時稅率／取整欄全空，啟用時必須完整且通過資料庫範圍限制。A 公司更新不得改動 B，無 `settings.manage`、缺 signed CSRF、stale `updated_at` 與非法欄位分別固定拒絕，成功更新與 audit 必須同交易。ADR-018 七類單號及報價／工單列印政策只讀且不可由 PUT 改寫；React 驗證權限、載入、錯誤、存檔、政策表格、axe 與 RWD，實際桌面瀏覽器另確認存檔及無整頁水平溢位。正式稅額計算、單號配發、對帳文件與列印 UAT 不得在此 Slice 宣稱完成。

Slice 2.3～2.5 客戶管理垂直驗收固定包含：同公司正規化代號不可重複、不同公司可使用相同代號、不存在或跨公司 ID 回 404、`customers.read／manage` 分別保護讀寫、unsafe request 必須通過 Origin＋signed CSRF、建立／修改／停用與 audit 同交易。查詢至少覆蓋代號、名稱、簡稱與狀態；React 覆蓋清單、空資料、錯誤、無權限、新增、編輯、唯讀及停用，並通過 axe、RWD、型別與 UI conformance。所有 fixture 必須虛構，不得使用 221 筆舊客戶內容。

## 4. 必測端到端案例

### E2E-01 直接建立工單

```text
登入
→ 選擇客戶
→ 直接建立工單
→ 填材料、印刷、製程、附件
→ 確認及列印
→ 查詢找到工單
```

預期：沒有報價也能完成；快照與來源正確。

### E2E-02 報價轉工單

```text
建立報價
→ 加入兩筆明細
→ A4 橫向預覽
→ 確認
→ 勾選兩筆明細建立一個案件
→ 系統建立兩張各自保留來源的子工單
→ 逐張調整並確認工單
```

預期：一個案件含兩張獨立工單；轉換重送不重複建立，報價後續變更不覆蓋案件或工單。

### E2E-03 部分完工與多次出貨

```text
工單數量 1,000
→ 一般製程完成（庫存仍 0）
→ 運送製程完成（庫存仍 0）
→ 最終完工 600（庫存 600）
→ 再完工 400（庫存 1,000）
→ 出貨 500＋備品 10（庫存 490）
→ 再出貨 300（庫存 190）
```

### E2E-04 出貨沖銷

取消第二次出貨後預期庫存回到 490；原出貨與負向流水仍存在，另有反向流水。

### E2E-05 並行出貨

庫存 100，兩個 session 同時各出貨 80；最多只有一個成功，庫存不得為負。

### E2E-06 防重複計價

兩個 session 同時計價同一出貨明細；最多一個成功，失敗者看到明確訊息。

### E2E-07 計價與價格記憶

建立基礎計價、加入版費與刀模費、更新預設價格；下一筆同客戶品項能看到來源、日期與建議，但不自動覆蓋。

### E2E-08 請款與部分收款

建立唯一對帳單，先驗證預設稅額為 0，再用明確啟用的另一案例驗證稅率及取整快照。對帳單進入已請款狀態後，登記部分收款再登記尾款；狀態依序為已請款、部分收款、已收款。

### E2E-09 權限

- Slice 1.6 先以 synthetic role／capability 驗證 allow、deny、停用立即失效、跨公司指派拒絕及 API／UI 雙層守門。
- 下列公司角色案例要等 P1-02 mapping 簽認後才成為正式 E2E fixture，不以候選角色名稱自行定案：
- 生產角色不能看收款。
- 會計不能修改已確認工單製程規格，除非權限矩陣允許。
- 一般操作員不能超量出貨、沖銷收款或管理使用者。

### E2E-10 跨公司

A 公司使用者即使猜到 B 公司 UUID，也不能開頁面、下載附件、修改、匯出或透過搜尋看到名稱。

Slice 1.7 基礎驗收另外固定：request body／query／header 的 organization 不影響 Session scope；A scope 對 B row 的 SELECT 為空、UPDATE 為 0 筆；CREATE 只歸屬 A，application code 傳入 organization 會在 SQL 前拒絕。後續每個 domain 仍須各自加入 A／B 交叉 fixture，不能只引用基礎測試代替。

### E2E-11 新舊單號

- 七類新文件都使用 ADR-018 格式，同時配號不重複。
- 不同公司各自配號，公司 A 的流水不佔用公司 B 的號碼。
- 日流水跨日、月流水跨月重置；各文件類型互不佔用。
- 日期修改不重編號，作廢不重用，另存新檔取得新號。
- 舊號不加前綴，畫面標示舊系統並可搜尋到新資料列。
- `SS` 第 100 筆／`SSS` 第 1,000 筆在同日或同月依 ADR-018 明確拒絕並通知管理者，不靜默擴位、重用或重號。

### E2E-12 出貨中補登完工

- 一般出貨庫存不足時拒絕，無有效運送完成事件、無專用權限、缺原因或數量不合法時同樣拒絕。
- 專用權限者輸入真實完工量後，獨立完工正向流水與出貨負向流水在同一交易完成，並以 correlation ID 追溯。
- 多明細任一步失敗整張 rollback；重送不重複建立；並行後不超扣且餘額不為負。
- 實際整批完工量可大於短缺量；累計超過訂購量時必須警告、二次確認及保存原因。
- 出貨取消不自動沖銷真實完工；Import 不產生合成補登事件。

## 5. 金額驗證

開工前由公司提供至少三張實際但可安全處理的對帳案例，轉成去識別測試 fixture：

1. 不含稅、無取整。
2. 含稅或稅額請款。
3. 每筆小計取整與總額取整有差異。

每個案例固定保存：

- 原始明細。
- 計算中間值。
- 預期小計。
- 預期調整。
- 預期稅額。
- 預期總額。

禁止只測最終總額而沒有中間值，否則錯誤可能互相抵銷。

## 6. 列印驗收

### 自動檢查

- 紙張尺寸及方向。
- 元件不超出 page box。
- 操作按鈕及導覽不出現在 print mode。
- 多明細正確分頁。
- 頁首／頁尾不遮住明細。
- 黑白 screenshot 對比可讀。
- 固定 fixture 的視覺差異在審核範圍內。
- 伺服器 PDF bytes 以 `%PDF-` 開頭，下載長度與 SHA-256 等於不可變 metadata；同一來源／模板版本重用，來源或工單附件版本異動另建。
- PDF 使用內嵌繁中字型，以 Poppler 在不依賴主機 Adobe CNS language pack 的環境轉成 PNG，逐頁檢查裁切、框線、方向與中文字。
- 產生與下載都驗證公司 scope 及來源文件 read capability；A 公司不能以 B 公司的 export ID 下載。

### 實體印表機

每一種正式文件至少在公司實際印表機測試：

- 100% 縮放。
- 瀏覽器預設頁首頁尾關閉。
- 中文字型正確。
- 框線、欄位及圖片不截斷。
- 黑白列印不依賴顏色辨識。

簽認文件：報價、工單、出貨單、對帳單（請款為狀態）。

## 7. 效能與容量基線

第一版不追求大量壓測，但要以代表資料量驗證：

- 兩位使用者同時登入及操作。
- 客戶至少 221 筆以上。
- 工單、製程、出貨及計價建立數年代表資料。
- 常用列表第一頁有分頁且不抓全部明細。
- 關鍵字搜尋有 query plan 紀錄。
- 備份執行時核心操作仍可接受。

Phase 9 本機基線（2026-08-15）：在既有測試資料上額外建立 300 筆同公司客戶後，整合搜尋必須在 2 秒內回應，且包含 Session 驗證、capability 解析、客戶與報價搜尋在內最多執行 5 個 SQL statement；每一類結果最多 50 筆，最終合併結果也最多 50 筆。此為回歸門檻，不代表正式主機容量承諾；Phase 10 全量 dry-run 後須以實際資料量重新執行 `EXPLAIN (ANALYZE, BUFFERS)` 並記錄慢查詢。

## 8. 備份與還原驗收

至少每季及正式切換前：

1. 建立全新 VM 或乾淨本機環境。
2. 只使用 README、Git remote／bundle、備份檔與 Secret 還原說明。
3. 還原 PostgreSQL。
4. 還原附件及文件快照。
5. 執行 migration。
6. 登入並跑 E2E smoke。
7. 抽樣開啟歷史附件與列印文件。
8. 建立測試出貨、計價及收款。
9. 記錄開始／完成時間、失敗點及 RPO／RTO。
