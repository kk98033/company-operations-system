| ADR-020 | 瀏覽器登入採 HttpOnly Session Cookie＋Session-bound signed double-submit CSRF＋exact public Origin；CSRF key 只由伺服器 runtime Secret 注入 | raw token 不暴露給 React／JSON；密鑰不進 Git／image／VITE，本機用 gitignored `.env`，正式環境用 owner-only 環境檔或 Secret Manager | 改為跨來源部署、全面本機 HTTPS、導入不同身分供應者，或需要無登出輪替多把 key |
| ADR-021 | 權限採公司角色＋精確動作 capability，DB 複合外鍵隔離且 API deny-by-default | 不讓角色名稱散落程式、UI 隱藏取代 API 授權或跨公司誤綁；P1-02 前不寫死 mapping | 公司簽認角色矩陣、需要 row-level policy 或導入外部 IdP／授權服務 |

| ADR-023 | 關鍵異動與 append-only 稽核同 transaction，Request ID 由 server 產生且稽核 payload 雙重遮罩 | 避免已修改但無稽核、跨公司 actor 與 Secret 永久落庫；client 不可偽造追蹤 ID | 導入外部集中稽核、法規要求 WORM storage，或安全事件需獨立保留 transaction |
| ADR-024 | 登入第五次失敗開始短期限制；狀態與事件只保存公司範圍 HMAC 指紋 | 限制密碼猜測、避免帳號存在性與原始 credential 落庫，且 A／B 公司不互相鎖定 | 正式公開網路需要可信 proxy／來源限流、導入 IdP，或實測門檻影響正常操作 |
| ADR-026 | 操作紀錄分成不可變業務 audit、append-only 資安事件與集中式 HTTP access／application log | 兼顧完整歸責、事件偵測、查詢量與敏感資料最小化；以 Request ID 串接 | 導入外部 SIEM／IdP 或法規要求不同保存／WORM 規則 |
| ADR-027 | 備份採 3-2-1、PITR／WAL、公司異地副本及定期乾淨還原；Secret 使用獨立復原程序 | 備份檔存在不代表可還原，DB／附件／程式／Secret 必須一起恢復 | 公司選定不同雲端、RPO／RTO 或法規保存要求 |

## 3. 風險處理規則

- 高影響且高可能性的風險不得只寫「之後注意」，必須對應 Slice、測試或待確認項目。
- 風險發生時在進度紀錄寫事件、影響、暫時處置及長期修正。
- 關閉風險需有證據，例如測試、簽認、還原報告或量測結果。
- 新風險若會改變架構，先新增 ADR，再修改程式。
