# UI 設計系統與通用版型

> 狀態：v1.3 正式基準（2026-08-12）｜決策：ADR-010
>
> 可操作示範：`http://127.0.0.1:5173/ui-patterns`
>
> 適用範圍：新版 React 系統的所有登入後頁面、對話框、抽屜與列印入口

> 登入頁是無側邊欄的身分邊界例外，仍必須沿用本文件的平面工業色彩、Tokens、`Field`、`SystemState`、按鈕、無障礙與 RWD；不可自建浮動陰影卡片或另一套登入設計系統。

> 公司 UI 驗收邊界（2026-08-09）：報價／工單 PDF 鎖定欄位、分區、順序、單頁操作及列印內容；螢幕介面採本設計系統的現代工業 ERP 視覺與 RWD，不逐像素複製 Windows XP。附件未明示的必填、預設值與上限不得自行加入。

## 1. 目標與使用情境

這不是一般行銷後台。主要使用者會在 Windows 桌面環境長時間處理客戶、報價、工單、生產、庫存、出貨、計價、請款及收款。因此 UI 的優先順序是：

1. 快速辨識目前模組、單據、狀態與下一步。
2. 在 1366×768 與 1280×720 仍能完成主要操作。
3. 清單資訊密度高，但表單必須有足夠間距避免誤填。
4. 從清單進詳細資料再返回時，不遺失查詢條件與位置。
5. 重要狀態、錯誤、作廢及沖銷能清楚區分並可追溯。
6. 未來增加公司或模組時，導覽不需整套重排。

不以「大量圓角卡片、漂浮陰影、玻璃背景、巨幅歡迎文字」作為主要視覺。這些元素會降低資料密度，也與每天操作的生產管理工具不相符。

## 2. 視覺方向

正式方向是「A 的平面工業 ERP 架構＋C 的表單留白＋B 的少量操作習慣」。

| 來源 | 採用 | 不採用 |
|---|---|---|
| A 平面工業 ERP | 深藍灰側欄、工業橙重點、平面邊界、密集清單、KPI 狀態 | 預覽中 330px 內層側欄、所有篩選硬塞一行 |
| B 現代桌面 ERP | 鍵盤操作、返回狀態保存、工作中脈絡 | 多層選單、滿版工具列、Windows XP 視覺 |
| C Bootstrap 企業版 | 表單欄距、分區、易讀留白 | Bootstrap 預設外觀、寬鬆卡片式首頁 |

## 3. Design Tokens

實作來源為 `frontend/src/styles/tokens.css`。頁面不得直接大量新增近似顏色或間距；新增 token 前先說明用途。

### 3.1 色彩

| Token／用途 | 基準色 | 使用規則 |
|---|---:|---|
| Brand 950 | `#0b2638` | 主側欄底色 |
| Brand 900 | `#102f47` | 深色標題、主要 hover |
| Brand 700 | `#205273` | 主要按鈕、進行中、連結 |
| Brand 100 | `#dceaf2` | 淺色選取／進行中背景 |
| Accent 600 | `#ad651c` | 交期提醒、選中底線、需要注意 |
| Success 600 | `#2f7654` | 已完成、正常、成功 |
| Danger 700 | `#a43e3e` | 錯誤、逾期、作廢前警告 |
| Ink 900 | `#17222b` | 主要文字 |
| Ink 700 | `#40505d` | 次要說明 |
| Ink 500 | `#697985` | 輔助資訊、時間、placeholder 說明 |
| Canvas | `#eef1f2` | 頁面底色 |
| Surface | `#ffffff` | 表單、表格、內容區 |
| Border | `#cbd4d9` | 一般分隔線 |
| Border Strong | `#9dabb3` | 表格固定欄、查詢容器、重要邊界 |

狀態色永遠搭配文字或圖示。禁止只把整列染紅／染黃卻沒有「逾期」「待核定」等狀態文字。

### 3.2 字體與數字

- 字體順序：Inter、Noto Sans TC、PingFang TC、Microsoft JhengHei、system-ui。
- 頁面 H1：28–36px responsive；區塊標題 15–16px；內文 12–14px。
- 清單資料 12px 起，必要時由使用者密度偏好提高，不可低於 12px。
- 工單號、數量、金額、日期使用等寬數字特性 `font-variant-numeric: tabular-nums`。
- 金額靠右；數量靠右；文字靠左；純日期可靠左，表格全站保持一致。
- 禁止用全大寫英文取代中文功能名稱；英文 eyebrow 只作模組脈絡。

### 3.3 間距與密度

基準間距為 4px 倍數：4、8、12、16、20、24、32、40px。

| 項目 | 基準 |
|---|---:|
| 頁面外距 | 桌面 24px；窄視窗 16px |
| 區塊間距 | 20px |
| 表單欄水平距 | 24px |
| 表單列垂直距 | 20px |
| 控制項高度 | 36px |
| 清單列高 | 40px |
| 表格儲存格水平 padding | 12px |
| 區塊內容 padding | 20px |

總覽與清單可較密；新增／編輯表單不可為了塞進一畫面而把欄位縮到難以辨識。

### 3.4 邊界、圓角與陰影

- 內容分區以 1px 邊界與底色分層。
- 一般控制項 2px 圓角；特殊容器最多 4px。
- 主卡片、KPI、表格及側欄不使用陰影。
- 狀態標籤不是膠囊；使用 3px 左邊線、小色塊與文字。
- 使用者頭像可為方形；只有真正圓形語意（例如線上狀態點）才用 50%。

├────────────────────────────┼────────────────────────────────────┤

│ ．首頁                      ├────────────────────────────────────┤
│ ．客戶與報價                │ 頁面內容（依通用版型）                │
│ ．工單與生產                │                                    │
│ ．庫存與出貨                │                                    │
│ ．計價與請款                │                                    │
│ ．設定／稽核                │                                    │

### 4.1 側欄

- 展開寬 248px；收合寬 72px。
- 主模組最多兩層。第三層功能改由頁內頁籤或區塊導覽呈現。
- Active 項目使用工業橙邊線＋藍色底，不只改文字顏色。
- 尚未實作又沒有展示說明頁的功能只能顯示為 disabled 說明；主模組可連到明確標示「展示資料／功能尚未啟用、未連 API／資料庫」的說明頁，不得假裝已能執行業務操作。
- 公司切換器若未來需要，放在品牌區下方，不與使用者帳號混在一起。
- 1024px 以下預設收合；736px 以下改成頂部三欄流程導覽，所有入口仍須可鍵盤操作，文字不可因水平捲動而消失。

### 4.1.1 Phase 0 主模組路由目錄

`frontend/src/app/workflowModules.ts` 是主流程名稱、順序、路徑與原型責任的單一來源；Router、側邊欄及頁內流程不得各自維護另一份清單。

| 順序 | 模組 | 路徑 | 正式實作 Phase |
|---|---|---|---|
| 1 | 客戶管理 | `/customers` | Phase 2 |
| 2 | 報價管理 | `/quotations` | Phase 3；由客戶直接建工單時可略過 |
| 3 | 案件管理 | `/cases` | Phase 4；集中同一客戶訂單或報價的子工單 |
| 4 | 工單管理 | `/work-orders` | Phase 4；一張工單一個主要品項 |
| 5 | 生產管理 | `/production` | Phase 5 |
| 6 | 庫存管理 | `/inventory` | Phase 5 |
| 7 | 出貨管理 | `/shipments` | Phase 6 |
| 8 | 計價管理 | `/pricing` | Phase 7 |
| 9 | 請款／對帳 | `/statements` | Phase 8 |
| 10 | 收款管理 | `/receipts` | Phase 8 |

Slice 0.8 原型頁只允許共用 `PageHeader`、`Section`、`StatusLabel`、`DefinitionGrid` 與 `DataTableFrame` 呈現模組責任、流程輸入／輸出及需求編號；案件頁可用同一表格版型示意一案件多工單。頁首、狀態、相鄰流程按鈕與 RWD 必須沿用 ADR-010。正式清單、表單、API 狀態與業務操作只能在對應 Phase 另建 feature，不得在通用原型元件堆疊業務邏輯。

### 4.1.2 系統管理正式路由

- `/settings/company` 使用「新增／編輯分區表單」版型，桌面為基本資料＋文件頁首預覽，1024px 以下轉單欄，390px 不得產生整頁水平捲動。
- 導覽與頁面都以 `settings.manage` gate 控制；UI 隱藏不取代 API 403。
- Logo 區只顯示 metadata 狀態；附件切片完成前不出現假上傳按鈕或可手填 object key。
- 預覽只確認共用抬頭資訊，不冒充報價單／工單完整列印稿；正式列印仍依 Gmail PDF 契約逐 Slice 驗收。

### 4.2 頂列

- 高 56px，白底、底邊線、無模糊效果。
- 左側：側欄收合、環境／公司脈絡。
- 右側：登入者、角色、通知或工作狀態；不放主要業務動作。
- 正式與測試環境必須有文字差異，不能只靠顏色。

### 4.3 頁首 PageHeader

- 必備：模組 eyebrow、H1。
- 選配：一句用途說明、狀態、次要操作、主要操作。
- 操作順序由左到右為低風險到高優先；主要按鈕放最右。
- H1 優先用使用者語言，例如「工單 WO-20260808-001」，不只顯示內部 route name。
- 建立／編輯頁可在頁尾重複主要儲存動作，但名稱與順序必須一致。

## 5. 通用版型

每個正式頁面開發前，必須先從以下版型選一種，再加入業務特有元件。不可每個 feature 自行重新發明頁首、表格或按鈕順序。

### 5.1 總覽／工作台版型

用途：首頁、工單總覽、生產監管總覽、應收工作台。

排列：

1. PageHeader：頁面目的與主要入口。
2. KPI Strip：最多 4–6 個，全部可說明統計範圍。
3. 今日優先處理：以交期／異常排序。
4. 流程待辦：連到已套用篩選的清單。
5. 最近活動或異常摘要（確有需求才加）。

規則：

- KPI 只有總覽可用；不能為了填空間在每頁複製。
- KPI 必須可追到對應清單或說明計算定義。
- 金額與數量不可混成沒有單位的數字。
- 首屏優先呈現要處理的事，不用大面積歡迎區或裝飾圖。

### 5.2 清單／查詢版型

用途：客戶、報價、工單、生產、庫存流水、出貨、計價、請款、收款及稽核清單。

排列：

1. PageHeader：標題、匯出、新增。
2. FilterBar：高頻條件先顯示；低頻條件放「更多條件」。
3. 結果區標題：筆數、目前條件摘要、欄位設定。
4. DataTable：固定識別欄、排序、列操作。
5. Footer：顯示範圍、總筆數、每頁筆數與分頁。

查詢列：

- 使用 `repeat(auto-fit, minmax(168px, 1fr))`；不得寫死全部同一列。
- 關鍵字通常第一個，查詢／清除通常最後一組並靠右。
- 日期範圍拆成起日／迄日；錯誤要明確指出哪個日期。
- 查詢條件同步到 URL search params，讓重新整理、返回、分享內部連結仍可復原。
- 從詳細頁返回必須恢復分頁、排序、選取列及捲動位置。

表格：

- 第一個識別欄（工單號、客戶代號、單據號）`position: sticky; left: 0`。
- 重要欄位放前面：識別碼、客戶／對象、品名／主旨、數量／金額、目前狀態、交期。
- 低頻欄位可水平捲動或由欄位設定開啟，不能把關鍵欄放到最右才看得到。
- 每列只放 1–3 個最常用操作；其他動作進「更多」。
- 行內編輯只用於風險低且容易撤回的欄位。庫存、計價、請款、收款不得直接在表格任意覆寫。
- 整列可點時仍需有清楚的按鈕／連結，支援鍵盤與新分頁。
- 空狀態要區分「沒有資料」與「目前篩選無結果」。

`/audit-logs` 是第一個接正式 API 的清單版型：側欄入口只對 `audit.read` 顯示，後端仍獨立驗權；頁面固定提供 loading、空資料、錯誤重試與無權限狀態。表格優先顯示時間、動作、對象、文件號、操作者、結果、原因、前後值及 Request ID；前後值使用可展開的唯讀 JSON，不提供編輯、刪除或覆寫操作。窄視窗保留固定時間欄與水平捲動，查詢列轉為單欄。

### 5.3 新增／編輯表單版型

用途：客戶、報價、工單、出貨單、請款資料及設定。

排列：

1. PageHeader：取消、儲存草稿（若支援）、主要儲存。
2. 基本資料。
3. 依流程拆分的明細區，例如材料、印刷、製程、附件。
4. 風險摘要或計算預覽。
5. 頁尾操作列。

欄位規則：

- 桌面最多三欄；複雜或長文字欄位跨兩／三欄。
- 標籤放輸入框上方，避免中英文長度造成垂直對不齊。
- 必填以「＊」和錯誤文字標示；不要只把邊框變紅。
- 數量與金額顯示單位、精度與負數規則。
- 動態明細採清楚的「新增一列／移除」；刪除既有正式紀錄需說明原因或作廢，不可靜默消失。
- 儲存失敗保留使用者輸入，並把焦點移到錯誤摘要或第一個錯誤欄。
- 離開有未儲存內容時提示；成功後以後端回傳資料為準。
- 表單不得顯示 KPI。

### 5.4 詳細資料／唯讀版型

用途：查看客戶、報價、工單、出貨、請款與收款。

排列：

1. PageHeader：單據號、狀態、列印、編輯。
2. 關鍵摘要列：客戶、交期、數量／金額、目前狀態。
3. 主要資料 DefinitionGrid。
4. 關聯流程或事件時間軸。
5. 明細表、附件、稽核紀錄。

規則：

- 顯示建立者、建立時間、最後修改者／時間。
- 作廢資料保留原值、作廢者、時間與原因，不能偽裝成刪除。
- 關聯單據用明確連結，例如報價明細→工單→出貨→計價→請款。
- 高風險操作放在獨立區或更多選單，且需要確認與原因。
- 詳細頁不得顯示總覽 KPI。

### 5.5 主從明細／工單工作頁

用途：工單材料、印刷、製程、完工、出貨明細與計價明細。

工單資訊架構固定區分「查詢入口」與「一張單據的整合工作頁」：

| 路由 | 責任 |
|---|---|
| `/work-orders` | 現行／歷史工單的單一查詢清單；提供關鍵字、日期及客戶條件，結果優先顯示工單號、客戶、品名、數量、單價、版費、刀模費及交期 |
| `/work-orders/new` | 新增工單；客戶、訂單、價格、備紙、印刷、製程、備註及圖片都在同一個 form |
| `/work-orders/:workOrderId/edit` | 沿用同一張整合表單編輯，不另造第二套欄位與排列 |
| `/work-orders/:workOrderId` | 唯讀詳情、來源鏈、附件與稽核 |
| `/work-orders/:workOrderId/print` | 由同一筆快照產生 A4 列印，不重複建檔 |

- 「單頁」是使用者的一張完整工作頁，不代表把程式寫成一個大檔案；React 必須依基本資料、備紙、印刷、製程及附件責任拆成可測試元件，再由單一頁面組裝。
- 備紙、印刷、製程是工單內的規劃區段，不是側欄主模組，也不是必須逐步送出的 wizard。
- 生產管理只接手已儲存／確認工單的實際開始、完成、重開與最終完工事件，不重複保存工單規劃欄位。
- 長工單可使用可聚焦的頁內錨點；錨點同步 URL hash，不能只靠視覺捲動。

- 主資料摘要保持可見；明細依流程順序分區或頁內頁籤。
- 頁籤需同步 URL hash／search，重新整理仍回到原區。
- 不把所有欄位做成一張超寬表；每個明細區只呈現該任務必要欄位。
- 完工、出貨、計價等交易動作用對話框顯示「動作前、此次、動作後」數量摘要。
- 發生版本衝突時顯示最新值並要求使用者重新確認，不可覆蓋他人操作。

### 5.6 Modal 與 Drawer

Modal 適用：需要立即決策的短任務，例如確認完工、作廢、沖銷。已簽認的 P0-05 使用專用「補登完工並出貨」對話框，明示現有量、不足量、實際完工量與交易後餘額，不使用模糊的「強制出貨」。

Drawer 適用：不離開清單的輔助資訊，例如欄位設定、稽核摘要、附件預覽。

- Modal 不承載大型多區表單；超過約 8 個欄位改成正式頁面。
- 危險動作按鈕清楚寫「作廢工單」而不是模糊的「確定」。
- 必須有標題、說明、關閉、焦點鎖定、Esc 規則與關閉後焦點回復。
- 未儲存資料不得因點背景誤關閉。

### 5.7 Loading、空、錯誤、無權限狀態

| 狀態 | 呈現 |
|---|---|
| 初次 Loading | 保留頁面骨架，表格顯示列骨架或明確載入文字 |
| 背景更新 | 保留舊資料並顯示小型更新狀態，不閃成整頁空白 |
| 尚無資料 | 說明如何建立第一筆，若有權限提供主要動作 |
| 篩選無結果 | 顯示目前條件，可清除條件，不誤導成系統沒有資料 |
| API 錯誤 | 簡短原因、request id、重試；保留輸入或舊資料 |
| 權限不足 | 說明缺少哪類權限與可聯絡對象，不暴露敏感資料是否存在 |
| 已被他人更新 | 顯示差異或最新摘要，要求重新載入再提交 |

### 5.8 列印版型

- 報價、工單、出貨單、對帳單使用獨立 print route，不直接列印操作頁。
- 預覽使用 A4 實際尺寸、固定分頁規則、頁首頁尾與模板版本。
- 列印畫面隱藏側欄、頂列、操作按鈕與互動狀態。
- 表格不得把單列切成兩頁；長備註需定義換頁行為。
- 需以公司實際印表機及既有樣張驗收，不只看瀏覽器 PDF。

## 6. 按鈕與操作層級

| 層級 | 範例 | 視覺 |
|---|---|---|
| Primary | 存檔、建立出貨單、確認完工 | 深藍實心；一個操作區通常只有一個 |
| Secondary | 取消、列印、匯出、清除 | 白底邊框 |
| Text | 查看、設定欄位、展開 | 藍色文字連結 |
| Danger | 作廢、沖銷 | 危險色；需要確認與原因，不與一般 Primary 並排混淆 |

- 「返回」是導覽，不寫成「取消」；「取消」只代表放棄尚未提交的操作。
- 按鈕文字使用動詞＋對象，避免只有「確認」「處理」。
- 非同步提交期間按鈕防重複；公司文件建檔頁文字改為「存檔中…」，其他動作沿用各自名稱，但不可清空整頁。
- 成功後顯示結果與可追蹤的單據號。

## 7. 響應式與公司螢幕基準

| 尺寸 | 驗收重點 |
|---|---|
| 1920×1080 | 內容不過度拉寬；表單維持可讀欄寬 |
| 1366×768 | 主要按鈕不裁切；重要表格欄位首屏可見 |
| 1280×720 | 側欄可收合；FilterBar 自動換行 |
| 1024px 以下 | 側欄固定收合；雙欄內容轉單欄 |
| 736px 以下 | 頂部降級導覽；表單單欄；表格保留水平捲動與固定識別欄 |

工單整合頁為密集型例外：三欄在 1152px 以下轉兩欄，928px 以下頁內導覽轉三欄，736px 以下才全部轉單欄；不論斷點，整頁不得水平溢出。上表的 1024px 是一般雙欄版型預設，不要求每個密集表單提早變成單欄。

這是桌面優先內部系統；窄視窗必須能查看與完成基本任務，但不以手機作為高密度工單錄入的主要環境。

## 8. 無障礙與鍵盤

- 所有頁面一個 H1；區塊按階層使用 H2／H3。
- 提供「跳到主要內容」連結。
- 所有表單欄位有可點擊 label；必填與錯誤以文字呈現。
- 焦點外框不可被全域 CSS 移除；與背景至少清楚可見。
- 自訂頁籤、Modal、選單實作正確 role、aria-selected／aria-current 與鍵盤行為。
- Tab 順序跟視覺與流程一致；不得用正數 `tabIndex` 強行重排。
- 圖示按鈕必須有可讀名稱；資料表操作不只依賴 hover。
- 常用快捷鍵需先在頁面提示並避開瀏覽器／作業系統快捷鍵；B 方案只作習慣參考。
- 動畫保持短暫，並尊重 `prefers-reduced-motion`。

Slice 0.7b 已把上述規格落成正式基線：首頁、404 及 `/ui-patterns` 四種狀態由 axe-core 執行 WCAG A／AA 與 best-practice 掃描；每個正式路由只有一個 H1。版型切換使用 tablist／tab／tabpanel、aria-selected／aria-controls 與 roving tabIndex，支援左右方向鍵、Home、End；跳轉連結可把焦點送到 `main`，全域焦點外框為 3px。Slice 1.5 又將獨立 `/login` 納入相同 axe 基線，並以可點 label、必填文字、錯誤 `role=alert` 及窄螢幕單欄作為登入契約；Slice 1.8 再納入有權限的 `/audit-logs` 正式清單頁。JSDOM 無真實像素排版，因此自動掃描不假裝驗證色彩對比；顏色、焦點可見性與破版仍須在實際瀏覽器人工驗收。

## 9. 共用 React 元件對照

正式 public boundary 位於 `frontend/src/ui/UiPatterns.tsx`，頁面只能由此匯入。內部依責任拆成 `PagePatterns.tsx`、`FormPatterns.tsx`、`InformationPatterns.tsx` 與 `SystemState.tsx`；對應 CSS 依頁面、表單、資訊、系統狀態與版型示範拆檔，並由 `main.tsx` 依固定順序載入。後續可繼續拆分，但 public API、DOM／ARIA、Tokens、RWD 與載入順序必須保持相容。

| 元件 | 責任 | 不負責 |
|---|---|---|
| `PageHeader` | 標題、說明、頁級動作 | 權限判斷、API |
| `KpiStrip` | 總覽統計排列與 tone | 自行計算業務數字 |
| `Section` | 區塊標題、說明、內容邊界 | 頁面路由 |
| `FilterBar` | 查詢條件 responsive 容器 | URL state、查詢 API |
| `Field` | label、必填、hint 排列 | domain validation |
| `DataTableFrame` | 水平捲動與 footer | 排序、分頁、資料取得 |
| `StatusLabel` | 顏色＋文字的狀態外觀 | 決定狀態轉換 |
| `DefinitionGrid` | 唯讀 key/value 資料 | 編輯功能 |
| `SystemState` | 404、路由錯誤、render error 等一致狀態頁 | 錯誤上報與重試策略 |

未來預定：`SearchToolbar`、正式 `DataTable`、`MoneyInput`、`QuantityInput`、Picker、`AuditTimeline`、`AttachmentPanel`、`PrintPreview`、`DangerActionDialog`。這些必須沿用本文件規格。

## 10. 頁面狀態與 URL

- 清單查詢、排序、分頁、頁籤寫入 URL search params。
- 暫時展開／收合、欄寬、欄位顯示可放介面偏好；含公司範圍的偏好要帶 organization scope。
- 表單暫存由 React Hook Form 管理；後端資料由 TanStack Query 管理。
- API 成功後使用回傳或重新查詢結果，不在前端自行推導庫存或帳務最終值。
- 返回清單要恢復捲動位置；跨登入或跨公司不恢復可能洩漏脈絡的狀態。

## 11. Do／Don't

| Do | Don't |
|---|---|
| 用邊線、底色與間距建立層級 | 每個區塊都做大圓角浮卡 |
| 一頁一個明確主要動作 | 同區放三四個同色主要按鈕 |
| 重要識別欄固定、狀態有文字 | 把工單號捲走或只用紅黃綠點 |
| 查詢條件可換行、可復原 | 全部塞一排或返回就清空 |
| 表單按流程分區 | 把 30 個欄位放一張無分區表 |
| 危險交易顯示前後數量及原因 | 直接覆寫庫存／金額或刪除紀錄 |
| 假資料明確標示 | 把公司正式資料放進測試與截圖 |
| 共用 tokens 與元件 | 每個 feature 自訂一套藍色、間距與按鈕 |

## 13. 變更本規格

小幅修正（間距、顏色可讀性、元件 bug）可在 Slice 中更新本文件。若要改變側欄架構、主要版型、元件庫、狀態語意或跨模組操作模式，必須新增／取代 ADR-010，並先更新 README、架構與測試基準。

### 13.1 禁止一次性自創 UI

正式頁面必須從本文件第 5 節選擇版型，並使用 `frontend/src/ui/`。遇到既有元件不足時依以下順序處理：

1. 先確認能否由現有元件組合完成，不能只因個人偏好另做一套。
2. 記錄跨模組都可能需要的缺口、狀態與操作案例。
3. 在 `frontend/src/ui/` 擴充通用 API，命名不得綁定單一客戶或單一 feature。
4. 只使用 `tokens.css` 的顏色、間距、圓角、控制高度與殼層尺寸。
5. 同時定義 loading、空、錯誤、disabled、readonly、權限及衝突狀態。
6. 同時完成桌面、收合側欄、雙欄轉單欄及窄視窗行為。
7. 補元件／頁面測試、人工尺寸驗證與本文件；若改變主要互動模式則新增 ADR。

不得先在 feature CSS 做完，再說「以後有空才抽共用」。無法證明通用性的 UI 不得成為正式基準。

### 13.2 自動守門

前端提供：

```bash
npm run check:ui
npm run test:a11y
```

而 `npm run lint` 會一併執行。現階段自動阻擋：

- 正式頁面未引用 ADR-010 共用 UI。
- 正式頁面繞過 `UiPatterns.tsx` public boundary，直接引用內部責任檔。
- JSX inline style。
- 已淘汰的 `panel`、`system-message`、`empty-state` 與舊按鈕 class。
- `backdrop-filter` 玻璃效果。
- 非 `none`／`inset` 的 box shadow。
- 未使用圓角 token 的 border radius。
- 缺少雙欄降級、窄視窗、收合側欄或 sticky 識別欄的基準規則。
- 正式共用 React module 超過 200 行，或共用 UI style module 超過 500 行。
- 共用 UI CSS manifest 與實際檔案不一致，或 `main.tsx` 的完整樣式載入缺少、重複、順序錯誤。
- 正數 `tabIndex`、缺少全域 focus-visible、跳轉連結／main 目標或 reduced-motion 降級。

`npm run test:a11y` 另外以 axe-core 掃描目前正式路由與 UI 狀態；新增正式路由或通用互動狀態時，必須同步加入掃描案例。axe 自動結果不能取代鍵盤、螢幕尺寸、色彩與公司實際工作流程的人工驗收。

`StylePreviewPage`／`style-preview.css` 只因保存 A／B／C 歷史比較而排除，畫面必須明確標示「不可作正式 UI」。新增其他例外必須先更新 ADR，不得直接修改檢查腳本繞過。
