# 資料模型與業務規則

> 本文件把最容易出錯的資料關聯、數量、金額與狀態規則獨立列出。實作 service、migration 及測試時必須引用對應規則編號。

## 1. 核心關聯

```mermaid
erDiagram
    ORGANIZATION ||--o{ CUSTOMER : owns
    ORGANIZATION ||--o{ USER_MEMBER : has
    CUSTOMER ||--o{ QUOTATION : requests
    QUOTATION ||--|{ QUOTATION_ITEM : contains
    CUSTOMER ||--o{ PRODUCTION_CASE : owns
    QUOTATION o|--o{ PRODUCTION_CASE : creates
    PRODUCTION_CASE ||--|{ WORK_ORDER : groups
    QUOTATION_ITEM o|--o{ WORK_ORDER : converts_to
    CUSTOMER ||--o{ WORK_ORDER : orders
    WORK_ORDER ||--o{ WORK_ORDER_MATERIAL : uses
    WORK_ORDER ||--o{ WORK_ORDER_PROCESS : requires
    WORK_ORDER ||--o{ FINAL_COMPLETION : completed_as
    FINAL_COMPLETION ||--|| INVENTORY_LEDGER : posts
    WORK_ORDER ||--o{ SHIPMENT_ITEM : ships
    SHIPMENT ||--|{ SHIPMENT_ITEM : contains
    SHIPMENT_ITEM ||--o| PRICING_ITEM : base_priced_as
    PRICING_DOCUMENT ||--|{ PRICING_ITEM : contains
    PRICING_ITEM ||--o| STATEMENT_ITEM : billed_as
    STATEMENT ||--|{ STATEMENT_ITEM : contains
    RECEIPT ||--o{ RECEIPT_ALLOCATION : allocates
    STATEMENT ||--o{ RECEIPT_ALLOCATION : receives
```

所有業務表都屬於一個 `organization_id`。外鍵關聯除了 ID，也必須驗證來源與目標在同一家公司。

## 2. 文件與來源規則

### DOC-01 單號

- 新版顯示號：`QUO-YYYYMMDD-SS`、`CASE-YYYYMMDD-SSS`、`WO-YYYYMMDD-SSS`、`SHP-YYYYMM-SSS`、`PRC-YYYYMMDD-SSS`、`STM-YYYYMM-SSS`、`RCT-YYYYMMDD-SSS`。
- `SS`／`SSS` 為各公司、文件類型與日／月期間獨立數字流水，從 `01`／`001` 開始。
- 同公司、同文件類型內唯一。
- 在資料庫交易內配置。
- 作廢後不得回收重用。
- 文件日期修改不自動更換已配發單號。
- 另存新檔一定取得新單號並保存 `source_document_id`。
- 內部主鍵不使用顯示號。舊資料保存 `legacy_document_number`、`legacy_source_table`、`legacy_source_key`，可顯示與搜尋，不追加新前綴。

### DOC-02 文件快照

報價確認、工單確認／列印、出貨確認、計價確認及對帳發行時，保存當時使用的：

- 公司抬頭。
- 客戶名稱、聯絡、地址及統編。
- 文件明細與價格。
- 稅別、稅率、取整方式。
- 模板版本。
- 操作者及時間。

歷史文件預設由快照重建，不重新讀取目前客戶主檔。

- 報價與工單新建介面不顯示或計算稅額。
- `statement` 是唯一正式對帳文件；請款是狀態。計稅預設關閉，啟用時保存稅率與取整快照。

### DOC-03 直接建工單與轉工單

- `production_cases` 是客戶訂單／報價的管理容器；一個案件含一張或多張工單，一張工單只屬於一個案件。
- 一張工單只保存一個主要品項；品項自己的數量、材料、印刷、製程、價格、完工、庫存及出貨不可和其他工單混用。
- 報價轉工單時，一次選取 N 筆明細會在同一交易建立一個案件與 N 張工單；每張保存各自的 `source_quotation_item_id`，不得合併成一張多品項工單。
- 直接建立工單時服務會自動建立單工單案件，`source_quotation_item_id` 為空；操作 UI 不增加一道必填案件表單。
- 報價日後修改不得自動覆蓋既有工單。
- 轉換命令必須使用 idempotency key；同一報價明細已有有效轉換時，預設拒絕重複建立並回傳既有案件／工單關係。
- 案件只保存分組、來源、交期與摘要狀態，不直接寫庫存；進度由有效子工單推導。

### DOC-04 工單製版規格

- 製版製程保留協力廠與製程說明。
- `plate_version` 只能為 `new`、`existing` 或 `null`。
- `plate_rotation` 只能為 `top_bottom`、`left_right` 或 `null`。
- 版本與輪轉是兩個獨立維度，不得合併成四選一。
- 新建時兩者均無預設值；附件未授權後端依新舊版自動推導必填關係。
- 曬版、代版、留版、舊色別與裁紙值只存在於 legacy 歷史顯示，不進入新建編輯欄位。

## 3. 數量規則

### QTY-01 一般製程與最終完工分離

- `process_events` 只描述個別製程進度。
- `final_completion_entries` 才表示可入庫成品數量。
- 一般製程完成不得寫入 `inventory_ledger`。
- 第一版的 `record_final_completion` 需要對應「運送」製程已完成，並由具權限者另行確認；運送事件本身不自動入庫。

### QTY-02 庫存流水

| 事件 | 流水方向 | 必要來源 |
|---|---:|---|
| 最終完工入庫 | 正 | `final_completion_entry_id` |
| 完工沖銷 | 負 | 原完工紀錄 |
| 正式出貨 | 負 | `shipment_item_id` |
| 備品扣除 | 負 | `shipment_item_id` |
| 出貨取消／沖銷 | 正 | 原出貨流水 |
| 人工增加 | 正 | 調整單、原因、核准者 |
| 人工減少 | 負 | 調整單、原因、核准者 |

不可直接 UPDATE 或 DELETE 原流水來改餘額。

### QTY-03 可出貨量

```text
可出貨量 = SUM(同公司、同工單、所有有效 inventory_ledger.quantity)
```

可在讀取模型建立 cache／summary，但 ledger 是最終真相；summary 必須能重建與對帳。

### QTY-04 出貨與備品

已定案：

```text
實際扣庫量 = 正式出貨量 + 備品量
```

保存三個欄位，不只保存合計。後續基礎計價只以正式出貨量為預設基礎；備品只有計價明細明確保存可請款數量與單價時才收費。

### QTY-05 出貨交易

建立出貨必須在同一交易中：

1. 鎖定來源。
2. 重新計算可出貨量。
3. 比較實際扣庫量。
4. 若可出貨量不足，一般路徑拒絕出貨，且不建立負庫存 override。
5. 只有已有有效運送完成事件、具 `shipment.complete_and_confirm` 權限且輸入真實完工量與原因時，才可在同一交易先建立獨立 `final_completion_entry` 與正向流水。
6. 寫整張出貨與負向流水；多明細任一步失敗全部回滾，交易後庫存必須非負。
7. 完工與出貨以 correlation ID、idempotency key 串接並寫 audit；累計完工超過訂購量時需警告與原因。
8. 取消出貨不自動沖銷真實完工；Import 不合成此類事件。

### QTY-06 數量案例

| 步驟 | 事件 | 變動 | 可出貨量 |
|---:|---|---:|---:|
| 1 | 最終完工 600 | +600 | 600 |
| 2 | 第二次完工 400 | +400 | 1,000 |
| 3 | 正式出貨 500、備品 10 | -510 | 490 |
| 4 | 第二次正式出貨 300、備品 0 | -300 | 190 |
| 5 | 取消第二次出貨 | +300 | 490 |
| 6 | 人工盤減 5 | -5 | 485 |

任何實作只要無法得到上表結果即不得完成。

## 4. 計價規則

### PRICE-01 基礎計價唯一

- 每個有效 `shipment_item` 最多有一個有效「基礎計價」明細。
- 以資料庫部分唯一索引保護，不只在 UI 隱藏按鈕。
- 手動增加的版費、刀模費、運費等明細可沒有 `source_shipment_item_id`，但保留所屬計價文件與建立者。

### PRICE-02 價格歷史

價格建議至少顯示：

- 客戶。
- 品名／規格。
- 計價內容。
- 數量與單價。
- 使用日期。
- 來源計價單與出貨單。
- 是否為目前預設。

價格歷史不可因更新預設而刪除。

### PRICE-03 金額精度

- DB 使用 `NUMERIC`。
- API 使用十進位字串。
- 後端以 Decimal 計算。
- 前端可顯示格式化數字，但不得用 binary float 作最後金額。
- 單價顯示精度、計算精度與最後取整精度分開設定。

## 5. 請款與收款規則

### BILL-01 對帳來源唯一

- 每個有效 `pricing_item` 最多出現在一個有效 `statement_item`。
- 請款是 statement 的流程狀態。取消對帳後是否可重新納入，必須由狀態及有效唯一限制支援。

### BILL-02 金額快照

每張 statement 保存：

- `subtotal_before_rounding`。
- `rounding_adjustment`。
- `subtotal`。
- `tax_mode`。
- `tax_rate`。
- `tax_amount`。
- `grand_total`。
- `rounding_policy`。

正式欄位名稱可調整，但以上語意不可遺漏。

- 新 statement 的 `tax_mode` 預設為不計稅。
- 只有明確啟用時才計算稅額；稅率與取整政策來自當次設定並快照，不硬編 5%。

### BILL-03 收款分配

```text
有效分配合計 <= 收款有效金額
單張對帳單有效分配合計 <= 對帳單總額
未收餘額 = 對帳單總額 - 有效分配合計
```

- 一筆收款可分配多張對帳單。
- 一張對帳單可由多筆收款逐次清償。
- 沖銷收款會使相關對帳單未收餘額恢復。
- 不直接覆寫 statement 的「已收金額」作唯一真相，可保存可重建摘要。

## 6. 狀態與作廢

### STATE-01 Command 型狀態轉換

不得提供能任意把 `status` 改成任何字串的通用 API。使用明確 command：

- `confirm_work_order`
- `cancel_work_order`
- `record_final_completion`
- `reverse_final_completion`
- `confirm_shipment`
- `reverse_shipment`
- `confirm_pricing`
- `issue_statement`
- `record_receipt`
- `reverse_receipt`

### STATE-02 高風險操作

以下操作必填原因並稽核：

- 作廢文件。
- 沖銷完工、出貨、計價、請款、收款。
- 重開已完成製程。
- 人工庫存調整。
- 「出貨中補登完工」（已簽認；這是兩個獨立業務事件的原子交易，不是負庫存例外）。
- 變更已確認文件的可修改欄位。
- 更新預設價格。

### STATE-03 後續資料保護

- 已有出貨的完工不得直接取消；需處理後續關聯。
- 已有計價的出貨不得直接沖銷。
- 已有請款的計價不得直接取消。
- 已有收款的請款不得直接取消。
- UI 顯示阻擋原因；API 回傳穩定錯誤代碼。

## 7. 並行與版本

- 主要表有 `version`。
- 一般編輯使用 optimistic locking；版本不符回傳 conflict。
- 出貨、單號、計價、請款與收款等資源競爭操作使用資料庫鎖與唯一限制。
- 高風險 POST 支援 idempotency key 時，相同 key 與相同 payload 回同一結果；不同 payload 必須拒絕。

必測並行情境：

1. 兩人同時配發單號。
2. 兩人同時出貨同一庫存。
3. 兩人同時計價同一出貨明細。
4. 兩人同時請款同一計價明細。
5. 使用者重按完工或收款按鈕。

## 8. 刪除、封存與資料保留

- 草稿且沒有任何後續關聯的測試資料，是否允許 hard delete 仍以環境與權限限制；正式資料預設不 hard delete。
- 確認過的文件只能取消／作廢。
- 歷史工單用 `archived_at` 或狀態，不搬到另一張 history 表後刪除原資料。
- 停用主檔不得破壞歷史外鍵；停用項目不再出現在新建選單，但歷史可顯示。
- P0-10 要求全年份舊資料都被處理；每筆來源必須標記為正式匯入、只讀封存、合併／重複 mapping 或例外待處理。
- 無法安全轉換的亂碼或缺關聯資料不可靜默丟棄，也不可以空字串強塞正式欄位。

## 9. 租戶隔離

### AUTHZ-01 角色與 capability

- `permissions.code` 是全域、正規化的小寫動作名稱，例如 `settings.manage`；不接受角色名稱、`*` 或隱式管理員捷徑。
- `roles` 屬於單一公司；`role_permissions` 只表達授權，沒有模糊的 deny override。
- `organization_member_roles` 以公司＋成員、公司＋角色兩組複合外鍵拒絕跨公司指派。
- API 預設拒絕，必須明確通過 `require_capability()`；UI 的隱藏只是操作改善，不能取代 API 403。
- 停用角色、permission、membership、user 或 organization 時，既有 Session 不得繼續取得該 capability。
- P1-02 簽認前不建立正式角色對業務 capability 的 seed；測試只使用 synthetic mapping。

### TENANT-01 Context 來源

- 目前公司由經驗證 session 決定。
- 不信任 request body 的 `organization_id`。
- 建立資料時由後端注入公司 ID。
- `OrganizationScope` 同時保存 organization、membership 與 actor；只允許 `require_organization_scope` 從 active Session 建立。

### TENANT-02 外鍵與唯一

- 單號、客戶代號等唯一條件包含公司 ID。
- 查詢、修改、下載附件及匯出都包含公司 scope。
- 必要時使用複合外鍵或 service 檢查避免跨公司關聯。
- SELECT／UPDATE／DELETE 使用 model-bound scope predicate；CREATE 不接受 caller 自行提供 `organization_id`。
- 單筆 ID 不存在或屬於別家公司時，對外使用相同 not-found 語意，不揭露另一家公司是否存在該資料。

### TENANT-03 測試

每個主要模組至少一個 A／B 公司讀取拒絕和寫入拒絕測試。

## 10. 稽核內容

Audit 至少包含：

- organization、actor、action。
- entity type、entity id、document number，適用時。
- timestamp、request id、來源 IP 摘要，依隱私政策。
- before／after 的必要欄位。
- reason。
- success／failure 類型，依安全事件需要。

不得保存：

- 明文密碼或密碼雜湊。
- Session ID、Cookie、CSRF token。
- Cloud 金鑰與 Secret。
- 完整檔案內容。
- 與稽核無關的大量敏感個資。

### AUDIT-01 已實作契約

- `audit_logs` 以 organization scope 保存 actor membership／user、action、entity、文件號、必要 before／after、reason、狀態、Request ID 與時間；actor 複合外鍵拒絕跨公司組合。
- 修改 service 必須在同一 transaction 先完成業務異動並 stage audit，不由 audit service 自行 flush／commit。任一步失敗時兩者一起 rollback；不得在交易成功後才以 best-effort 補寫。
- PostgreSQL trigger 拒絕一般 UPDATE／DELETE；正式 application role 不授予 TRUNCATE、trigger disable 或 DDL。更正只能新增補充／反向事件，不覆寫既有稽核。
- 遞迴 sanitizer 限制深度、筆數與文字長度，並遮罩 password／hash、Cookie、CSRF、Session、Token、Secret、private key、API key、bytes／檔案內容；唯讀 API response 再做一次防禦性遮罩。
- Request ID 由 middleware 每次產生 UUID，不採信 client 的 `X-Request-ID`；成功與錯誤 response 都帶同一 ID，未預期錯誤 log 只記 exception type 與 Request ID，不記 exception message。
- `/api/v1/audit-logs` 只接受 active Cookie Session，要求 exact `audit.read`，以目前 organization 查詢且最多 100 筆／頁；React `/audit-logs` 對無權限者不發 request。
- `failure` 事件只可由明確定義的安全事件 transaction 寫入。和業務失敗一起 rollback 的普通 command 不得宣稱會留下成功稽核；Slice 1.9 再定義登入失敗安全事件。
