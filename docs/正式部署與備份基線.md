# 正式部署與備份基線

> 版本：v1.0
> 基準日：2026-08-21
> 狀態：Phase 11.6 技術選型與 inventory 已建立；尚未建立付費雲端資源，RPO／RTO 尚待實際還原演練

## 1. 已選定的部署模型

系統維持一份 codebase 與同一套 release。A、B 公司不分叉程式，但正式環境必須各自使用獨立的雲端 project、App 部署、Cloud SQL、Cloud Storage、Secret、log 與備份。公司差異只透過公司設定、capability、功能開關、PDF 模板與 Import mapping 表達。

這可同時避免兩種問題：不必長期維護 A 版、B 版兩套程式，也不讓兩家公司的正式資料、登入 Cookie、帳密、附件與備份共用故障範圍。

## 2. A 公司正式環境基線

| 元件 | 正式基線 | 不採用的捷徑 |
|---|---|---|
| App | `asia-east1` GCE／等價 VM，Caddy＋React 靜態檔＋FastAPI；至少 2 GB RAM，依 11.13 壓測調整 | 不把開發用 Vite／reload server 當 production |
| PostgreSQL | Cloud SQL for PostgreSQL Enterprise、regional HA、private connectivity、SSD 自動擴充 | 不把 App VM 內的 Docker volume 當唯一正式 DB |
| DB 保護 | automated backup、PITR 7 天、每日加密 custom-format logical dump；刪除前 final backup | 不只做 VM snapshot 或單一 `pg_dump` |
| 附件／PDF | 11.7 後使用私人 Cloud Storage、soft delete／retention、object manifest＋SHA-256；移轉前 bytes 仍以 PostgreSQL 為 system of record | 不提供永久公開網址、不把備份只放同一台 VM |
| Secret | Secret Manager 固定版本＋最小 IAM；公司保有 break-glass 與輪替程序 | production `.env`、Secret、憑證不進 Git／image／普通備份包 |
| Log | stdout JSON access log 交給中央 log service；Request ID 關聯 audit／security event | 不記 query、body、Cookie、CSRF、密碼、token、DSN 或附件內容 |

Cloud SQL 官方將 regional HA 描述為跨兩個 zone 的 primary／standby 同步複寫，並建議 production 採 HA；標準／增強備份均支援 PITR，但 retention 與費用不同。Cloud Storage 對新部署優先用 soft delete 保護誤刪；若另開 Object Versioning，必須搭配 lifecycle，否則舊版本會持續計費。

## 3. 恢復目標與保存政策

- 目標 RPO：15 分鐘內；由 Cloud SQL PITR 提供主要能力。每日 logical dump 不是 15 分鐘 RPO 的替代品。
- 目標 RTO：4 小時內；只有 Phase 11.12 在乾淨環境實際計時還原後才能標示達成。
- Cloud SQL PITR logs：7 天；automated backup：30 天。
- 每日 encrypted logical dump：雲端異地保存 30 天；每週產生一份公司控制副本；每月保留一份離線／不可變副本，保存 12 個月。
- 高風險 migration、正式 Import apply 與上線切換前，另建立具名 restore point／on-demand backup。
- access log 暫定 30 天可搜尋；audit／security event 依資料庫與法規保存政策處理，不以 access log 取代。

上述數字是工程基線。若公司另有法規、合約或更長保存要求，須在建立資源前提高，不可事後以刪除中的資料補救。

## 4. 機器可讀 inventory

[backup-inventory.json](../infra/production/backup-inventory.json) 固定列出五類資產：PostgreSQL、私人 object storage、程式 release、production Secret 與營運 log。Inventory 只保存名稱、權責、保護方式及還原相依，不保存 Secret 值。

還原順序固定為：

1. 取得公司核准的 release tag、lockfiles 與 migration revision。
2. 建立隔離網路、Cloud SQL 與最小權限 service identity。
3. 取得指定復原點，還原 DB 並執行 schema／資料完整性檢查。
4. 還原／對帳 attachment、PDF object manifest、generation 與 SHA-256。
5. 由 Secret Manager 固定版本注入 Secret；若版本不可用則走 break-glass 重建及輪替，不能從普通備份檔找值。
6. 執行登入、工單、附件、出貨、帳務、audit 與歷史 PDF smoke／E2E；記錄實際 RPO／RTO。

## 5. 成本確認 Gate

現在不建立付費資源，也不在文件硬寫會變動的單一總價。正式採購前必須在 Google Cloud Pricing Calculator 以 `asia-east1` 匯出並由公司簽認下列月費項目：

| 項目 | 初始估算單位 | 成本變動因子 |
|---|---:|---|
| App VM＋boot disk | 1 台、至少 2 GB RAM | CPU／RAM、磁碟、egress、是否另建 standby |
| Cloud SQL regional HA | 1 組 primary＋standby | vCPU／RAM、SSD、HA、backup、PITR logs、egress |
| Cloud Storage | 依附件＋PDF＋備份實際 GB | location、storage class、soft delete／version、operation、egress |
| Secret Manager | 目前至少 4 類 Secret | active versions、access operations、rotation notifications |
| Central logging／monitoring | 依每日 request 與 retention | ingest GB、30 天查詢、alert／export |
| 公司異地副本 | 每週一份＋每月離線 | 儲存媒體、保管、加密與人工演練 |

Secret Manager 官方目前提供前 6 個 active versions 與每月 10,000 次 access 的免費額度，但不能把免費額度當永久預算保證。所有價格都以簽約／建資源當天的官方 Calculator export、幣別、稅與公司帳單為準。

若公司因成本拒絕 regional HA，可另簽「zonal 試營運」方案；該方案沒有 zone 自動 failover，不得對公司宣稱已符合相同 availability／RTO。正式業務資料仍建議採本文件的 managed HA 基線。
