# 程式碼與檔案命名規範

> 文件狀態：開發基準
>
> 適用範圍：`frontend/`、`backend/`、`e2e/`、`scripts/`、`docs/` 與 Alembic migrations
>
> 相關文件：`02_最終系統架構.md`、`docs/UI設計系統與通用版型.md`、`docs/decisions/ADR-010_統一UI設計方向.md`

## 1. 目的與優先順序

本規範用來讓 React、FastAPI、PostgreSQL 與舊資料 Import 程式共用一套可預測的名稱與邊界，避免功能增長後出現巨型檔案、重複型別與無法尋找的「萬用」函式。

規則衝突時的優先順序為：

1. 已簽認的業務規則與 ADR。
2. `02_最終系統架構.md` 的模組邊界與 API 契約。
3. `docs/UI設計系統與通用版型.md` 與 ADR-010 的 UI 規則。
4. 本文件的命名與拆檔規則。

如需例外，不可只在程式碼留一句 `TODO`；必須在當次 Slice 的進度紀錄說明原因、影響與收斂方式。若例外會改變跨模組架構或 UI 互動，需新增 ADR。

## 2. 共通原則

### 2.1 名稱要表達業務語意

- 使用完整英文業務名稱：`work_order`、`final_completion`、`pricing_document`。
- 只保留團隊已統一的縮寫，例如 `id`、`api`、`url`、`csv`、`dto`；不建立 `cust_mgr`、`woSvc`、`misc2` 這類名稱。
- 布林值使用 `is_`、`has_`、`can_`、`should_` 或對應的 camelCase：`is_active` / `isActive`、`can_reverse` / `canReverse`。
- 集合使用複數：`customers`、`workOrderItems`；單筆物件使用單數。
- 時間點用 `_at`，日期用 `_date`，區間用 `_from` / `_to`：`confirmed_at`、`delivery_date`、`created_from`。
- 金額與數量名稱必須表達單位或語意：`unit_price`、`shipped_quantity`、`tax_amount`，不用 `value1`、`num`、`amt2`。

### 2.2 檔案只有一個主要責任

「一個責任」是指一個明確的變更理由，不是指只能匯出一個 symbol。例如，`CustomerForm.tsx` 可包含與表單緊密相關的小型 private component，但不應同時負責 API mutation、權限決策與列印排版。

所有手寫程式碼適用以下拆檔檢查：

| 訊號 | 必須動作 |
|---|---|
| 檔案同時涵蓋兩個業務 aggregate，或同時做 HTTP、交易規則與排版 | 不論行數，先拆責任 |
| React component 超過 200 行，或有 3 個可獨立測試的區塊 | 拆成 page/container、section component 與 hook；不可只把 JSX 搬到另一個巨型檔 |
| hook 或 TypeScript 函式超過 60 行 | 抽出可命名的轉換、驗證或 state machine，並單獨測試 |
| Python module 超過 300 行，或 service 函式超過 60 行 | 依 command、query、validation 或 transaction use case 拆分 |
| Router 超過 8 個 endpoints，或處理不同子資源 | 依資源／use case 拆 router，再由模組 router 組裝 |
| CSS 同時定義全站基礎、多個通用元件與 feature 特例，或超過 500 行 | 依 tokens、layout、通用元件、feature 與 print 邊界拆分 |
| 新增手寫檔案超過 500 行 | 預設不得 merge；自動產生檔、純資料 mapping 或歷史比較檔例外須標示來源並不可手動擴寫 |

行數是 review gate，不是鼓勵無意義拆成一堆三行檔案。若拆檔後只會產生循環依賴或破壞 transaction 邊界，應在 review 說明並改拆其他責任。編輯既有超過門檻的手寫檔案時，不可繼續加大；當次 Slice 至少要停止惡化，並記錄拆分點。

### 2.3 依賴方向

- feature 可依賴 `frontend/src/ui/`、全域 tokens、API client 與測試工具；共用 UI 不可反向 import 特定 feature。
- FastAPI router 可依賴 schema 與 service；service 不可依賴 HTTP request/response 物件。
- domain/service 不可 import `tests/`、一次性 migration 或特定 UI 型別。
- Import reader、transform、mapping、apply 分開；不可讓 CSV parser 直接寫入正式業務表。

## 3. 專案層級的檔案與資料夾

| 對象 | 格式 | 範例 |
|---|---|---|
| 業務模組資料夾 | 對應既定 domain；TypeScript 用 kebab-case，Python package 用 snake_case | `features/work-orders/`、`modules/work_orders/` |
| 一般工具資料夾 | 全小寫，依責任命名 | `schemas/`、`services/`、`transforms/` |
| 環境與入口檔 | 依工具生態的習慣 | `main.tsx`、`main.py`、`compose.yaml` |
| 自動產生檔 | 保留 generator 命名，集中在 generated 邊界 | `services/generated/` |

不使用包含空白、日期版本或個人姓名的程式碼資料夾，例如 `new customer/`、`customer_v2/`、`kevin_utils/`。新舊契約切換由 API version、migration 與 Git 歷史表達，不靠 `final_v3` 檔名。

## 4. React 與 TypeScript

### 4.1 檔名與 symbols

| 對象 | 格式 | 範例 |
|---|---|---|
| React component / page / boundary 檔 | PascalCase `.tsx` | `CustomerListPage.tsx`、`CustomerForm.tsx`、`ErrorBoundary.tsx` |
| hook 檔與函式 | `use` + PascalCase/camelCase | `useCustomerSearch.ts`、`useCustomerSearch()` |
| 一般 TypeScript 檔 | lower camelCase `.ts` | `customerQueries.ts`、`queryClient.ts`、`formatMoney.ts` |
| 測試 | 被測檔名 + `.test.ts(x)` | `CustomerForm.test.tsx`、`formatMoney.test.ts` |
| component、type、enum | PascalCase | `CustomerForm`、`CustomerSummary`、`ShipmentStatus` |
| props | `<ComponentName>Props` | `CustomerFormProps` |
| 函式、變數 | lower camelCase | `buildCustomerFilters`、`selectedCustomerId` |
| 真正不變的模組常數 | UPPER_SNAKE_CASE | `DEFAULT_PAGE_SIZE` |
| Zod schema 值 | lower camelCase + `Schema` | `customerFormSchema` |
| 由 Zod 推導的表單型別 | PascalCase + `Values` | `CustomerFormValues` |

一般對象不使用 `I` 或 `T` 前綴：用 `CustomerSummary`，不用 `ICustomerSummary` 或 `TCustomerSummary`。不得用 `React.FC` 當成命名或 children 的替代；props 應明確定義。

### 4.2 feature 檔案邊界

業務 feature 依既有架構使用：

```text
features/customers/
├─ api/
│  ├─ customerQueries.ts
│  └─ customerMutations.ts
├─ components/
│  ├─ CustomerForm.tsx
│  └─ CustomerSearchFields.tsx
├─ pages/
│  ├─ CustomerListPage.tsx
│  ├─ CustomerCreatePage.tsx
│  └─ CustomerDetailPage.tsx
├─ schemas/
│  └─ customerFormSchema.ts
├─ types/
│  └─ customerUiModels.ts
└─ tests/
```

- page 組裝路由參數、query/mutation 與通用 UI 版型；不直接塞入數百行表單與表格實作。
- `frontend/src/ui/` 只放 ADR-010 跨模組通用元件。`CustomerPicker` 這類有業務語意但跨模組的元件，應有清楚 public API，不得讓 `ui/` 直接取得客戶 API。
- 只在形成穩定 public boundary 時建立 `index.ts` barrel；不建立會產生循環依賴的全 feature 萬用 barrel。
- OpenAPI 產生的 API request/response types 為契約來源；不可在 feature 重寫同名 DTO。UI 專用型別要命名為 `CustomerFormValues`、`CustomerRowViewModel` 等，明示它不是 API DTO。

### 4.3 React 函式與事件

- 元件事件 props 用 `on<Action>`：`onSubmit`、`onCustomerSelect`。
- 元件內部 handler 用 `handle<Action>`：`handleSubmit`、`handleCustomerSelect`。
- TanStack Query key factory 使用複數 domain：`customerKeys.list(filters)`；mutation 用明確動作：`useCreateCustomerMutation`。
- 不用 `data`、`item`、`result` 當長距離變數；範圍超過數行時改成 `customerResponse`、`shipmentRow`。
- 不以元件名稱綁定版面座標，例如 `LeftBox`、`BlueCard`；用 `CustomerSummarySection`、`StatusLabel`。

## 5. CSS 與 ADR-010 UI

| 對象 | 格式 | 範例 |
|---|---|---|
| CSS 檔 | kebab-case | `ui-patterns.css`、`customer-form.css`、`print-preview.css` |
| class | 語意化 kebab-case，元件子元素可用 `__` | `.ui-page-header`、`.ui-page-header__description` |
| variant | `--<variant>` | `.ui-button--primary`、`.ui-status--danger` |
| 狀態 | 優先使用語意 attribute；必要時 `is-` | `[aria-expanded='true']`、`.is-loading` |
| Design Token | `--<category>-<meaning-or-scale>` | `--color-border-strong`、`--space-4`、`--control-height` |

- 新元件必須使用 `tokens.css` 現有色彩、間距、圓角與控制高度；不在 feature 寫第二套視覺常數。
- 共用 class 使用 `ui-` 邊界；feature 根元素使用 domain 名，例如 `.customers-page`，並限制特定樣式在該邊界內。
- 不使用 `.red`、`.mt16`、`.box2` 這類只描述外觀或位置的 class。
- 每個正式頁面必須遵守 ADR-010 的 RWD、固定識別欄、無陰影、0/2/4px 圓角與通用版型；不因拆 CSS 而自創 UI。
- 媒體查詢與 print 規則放在相關 component/feature 樣式邊界，不用 `mobile-fixes-final.css` 續補。

## 6. FastAPI 與 Python

### 6.1 Python 命名

| 對象 | 格式 | 範例 |
|---|---|---|
| package、module | snake_case | `work_orders/`、`customer_service.py` |
| class、Pydantic model、SQLAlchemy model | PascalCase | `CustomerService`、`CustomerResponse`、`WorkOrder` |
| 函式、method、變數 | snake_case | `create_customer`、`expected_version` |
| 常數 | UPPER_SNAKE_CASE | `MAX_IMPORT_BATCH_SIZE` |
| private symbol | 單底線前綴 | `_normalize_customer_code` |
| type alias | PascalCase | `ReadinessCheck` |

依 PEP 8 與現有 Python 3.12 type hints；不在新程式碼混用 camelCase。縮寫在 class 中視為一個字，例如 `CsvReader`、`ApiClient`，不用 `CSVReader`。

### 6.2 模組責任

```text
backend/app/modules/customers/
├─ api.py
├─ models.py
├─ schemas.py
├─ services/
│  ├─ create_customer.py
│  └─ update_customer.py
└─ queries/
   ├─ get_customer.py
   └─ search_customers.py
```

小型模組可先使用單一 `services.py`；達到第 2.2 節門檻時再依 use case 拆成 `services/`，不為了目錄整齊預先建立空檔。

- `api.py` 只做 HTTP parsing、dependency injection、schema 與 service 呼叫。
- service 函式用明確 use case 動詞：`confirm_shipment`、`reverse_receipt`；不提供可任意改 `status` 的 `update_status`。
- query 使用 `get_`表示單筆且不存在是錯誤的操作，`find_`表示可回傳 `None`，`list_` / `search_` 表示複數與篩選。
- Repository 只在複雜查詢或隔離資料存取確實有價值時建立，不建立 `BaseRepository[Any]` 這類無語意抽象。
- 修改業務資料的 service 明確接收 actor 與 organization context，並由 service 決定 transaction 邊界。

### 6.3 Pydantic schema / DTO

API schema 使用資源名加用途：

- request：`CustomerCreateRequest`、`CustomerUpdateRequest`、`ShipmentConfirmRequest`。
- response：`CustomerResponse`、`CustomerListResponse`、`ShipmentConfirmResponse`。
- 共用內嵌資料：`CustomerSummary`、`PaginationMeta`。
- 不加無語意版本或層別後綴：`CustomerDtoV2`、`CustomerData`、`CustomerModelResponseBean` 均禁止。

像現有 `LiveResponse`、`ReadyResponse` 這類沒有 request body 的小型技術 endpoint 可使用簡短資源名；業務 schema 則使用上述明確後綴。

## 7. API route、JSON 與錯誤碼

### 7.1 Route

- 全部業務 API 位於 `/api/v1`。
- 資源路徑使用複數 kebab-case：`/work-orders`、`/pricing-documents`。
- path parameter 使用單數 snake_case 資源名：`/work-orders/{work_order_id}`，不用 `{id}` 或 `{workOrderId}`。
- query parameter 使用 snake_case：`delivery_date_from`、`customer_id`、`page_size`。
- CRUD 使用 HTTP method 表達動作，不寫 `/getCustomers`、`/create-customer`。
- 狀態轉換或高風險 command 可用動詞子路徑：`POST /shipments/{shipment_id}/confirm`、`POST /receipts/{receipt_id}/reverse`；其名稱必須對應資料模型的明確 command。
- Router 函式命名對應 use case：`list_customers`、`create_customer`、`confirm_shipment`。

### 7.2 JSON

- request/response 欄位統一 snake_case，與 Pydantic、PostgreSQL 與現有 API 一致。
- ID 欄位使用 `<resource>_id`；只有資源自身的主鍵在該物件頂層可命名 `id`。
- 日期為 `YYYY-MM-DD`，時間為含時區 ISO 8601。
- 金額與精確數量使用十進位字串，例如 `"unit_price": "1250.50"`，不使用 JSON binary float。
- 錯誤回應保持現有 `{"error":{"code","message","details"}}` envelope，不為單一 endpoint 自創結構。

### 7.3 錯誤碼

- 使用 UPPER_SNAKE_CASE，穩定且可由前端判斷：`VALIDATION_ERROR`、`VERSION_CONFLICT`、`SHIPMENT_INSUFFICIENT_STOCK`。
- 共通 HTTP / infrastructure 錯誤保留現有短碼：`NOT_FOUND`、`FORBIDDEN`、`SERVICE_NOT_READY`。
- 業務錯誤優先 `<DOMAIN>_<REASON>`：`WORK_ORDER_ALREADY_CONFIRMED`、`RECEIPT_ALLOCATION_EXCEEDS_BALANCE`。
- 錯誤碼不包含 HTTP status、中文或可變文案；`message` 給人閱讀，`code` 給程式判斷。
- 相同錯誤碼不可在不同情境改變語意。新錯誤碼必須同時有 API 測試與對應 UI 狀態。

## 8. PostgreSQL 與 Alembic

### 8.1 Schema 物件

| 對象 | 格式 | 範例 |
|---|---|---|
| table | 複數 snake_case | `customers`、`work_order_processes` |
| column | snake_case | `customer_code`、`confirmed_at` |
| primary key | `id` | `customers.id` |
| foreign key | 單數資源 + `_id` | `customer_id`、`work_order_id` |
| boolean | `is_` / `has_` | `is_active`、`has_spare_quantity` |
| unique constraint | `uq_<table>_<columns>` | `uq_customers_organization_id_customer_code` |
| foreign key constraint | `fk_<table>_<column>_<ref_table>` | `fk_work_orders_customer_id_customers` |
| check constraint | `ck_<table>_<rule>` | `ck_shipments_quantity_nonnegative` |
| index | `ix_<table>_<columns>` | `ix_work_orders_organization_id_delivery_date` |

- 每個公司範圍的 unique/index 要把 `organization_id` 寫進定義與名稱，不假設全系統唯一。
- 不使用 SQL 保留字、模糊縮寫或物理位置命名，例如 `order`、`cust_no2`、`field_1`。
- 舊系統原欄位名保留在 staging/source metadata，不擴散成新正式資料表的命名。

### 8.2 Alembic migration

- migration message 用小寫 snake_case 的明確動作：`create_customer_tables`、`add_expected_version_to_shipments`。
- 檔名保留 Alembic 產生的 `<revision>_<message>.py`；不手動改 revision/down_revision 來排版檔名。
- 一個 migration 處理一個可還原的 schema 意圖；不把數個業務模組塞進 `update_database.py`。
- `upgrade()` 與 `downgrade()` 都必須實作並測試；不在 application startup 自動執行 migration。
- 純資料 migration 要與 schema migration 分開，名稱說明 backfill 目的：`backfill_customer_search_name`。大量舊資料移轉仍使用 Import pipeline，不塞進 Alembic。

## 9. 測試命名

| 層級 | 檔名 | 測試名範例 |
|---|---|---|
| Vitest / RTL | `<Subject>.test.ts(x)` | `it('preserves filters when returning to the customer list')` |
| Pytest | `test_<subject>.py` | `test_confirm_shipment_rejects_insufficient_stock` |
| API integration | `test_<resource>_api.py` | `test_create_customer_returns_conflict_for_duplicate_code` |
| Playwright E2E | `<workflow>.spec.ts` | `work-order-to-shipment.spec.ts` |
| Import | `test_<reader_or_mapping>.py` | `test_uv_print_csv_preserves_source_row_number` |

- 測試名表達「條件／動作／結果」，不用 `test_1`、`works`、`basic test`。
- 用使用者可見行為命名，不把目前實作細節寫進測試名。
- fixture / factory 使用業務名：`customer_factory`、`confirmed_work_order`；不使用真實公司資料。
- 對高風險狀態轉換，正常、拒絕、並行衝突與稽核都應分別命名及測試。

## 10. 文件命名

- 主要管理文件保留現有中文名稱，讓公司與開發者都能找到：`UI設計系統與通用版型.md`、`舊資料移轉計畫.md`。
- ADR 使用 `ADR-NNN_簡短主題.md`，編號三碼且不重用。
- 進度保留在 `docs/progress/實作進度紀錄.md`，不另建 `progress-new-final.md`。
- README 使用大寫 `README.md`；每個子系統 README 只說明該邊界的使用方式，不複製整份主 README。
- 文件標題、索引名稱與檔名要一致；檔案新增、移動或取代時同步更新 `docs/README.md` 與相關連結。

## 11. 舊資料 Import 程式

依 `docs/舊系統資料Import對照與分批計畫.md` 的 `readers/`、`transforms/`、`mappings/`、`services/`、`reports/` 邊界：

| 責任 | 命名 | 範例 |
|---|---|---|
| 來源 reader | `<source>_<format>.py` | `uv_print_csv.py` |
| 單一純轉換 | 轉換對象複數或類別 | `dates.py`、`decimals.py`、`identifiers.py` |
| domain mapping | domain 複數 | `customers.py`、`work_orders.py` |
| 執行 use case | 動作名 | `run_dry_run`、`apply_customer_batch`、`reconcile_customer_counts` |
| batch/run 識別 | 穩定欄位 | `import_run_id`、`source_row_number`、`source_table` |
| report artifact | `<run-id>_<domain>_<report-type>.<ext>` | `ir_20260805_001_customers_reconciliation.json` |

- script 檔名使用明確動詞與範圍：`profile_uv_print_source.py`、`verify_customer_import.py`；不用 `import_all.py`、`fix_data.py`。
- CLI option 使用 kebab-case：`--dry-run`、`--source-manifest`；Python 內部對應 snake_case。
- dry-run、apply、reconciliation 是不同 use case，不得放在一個巨型 `main()` 中以布林值切換所有邏輯。
- 每筆 staging/error/mapping 記錄必須保留 `import_run_id`，並在該 scope 適用時保留來源檔、來源表與來源列號；run-level error 可不含檔／表／列，file-level error 必須含確切來源檔與表，row／field error 及 mapping 必須可回到確切 staging row。不靜默略過亂碼、轉換錯誤或 orphan。
- mapping 不連線寫入資料庫；apply service 不負責 CSV 解析；reconciliation 不修改資料。
- 轉換函式要盡可能保持 pure 且可重跑；禁止 `misc.py`、`helpers.py` 這類無邊界收容所。

## 12. 禁止巨型 `utils`、`helpers` 與 `types`

以下新檔案不得建立：

- 專案根目錄的 `utils.ts`、`helpers.py`、`common.ts`、`types.ts`。
- 包含多個 domain DTO 的 `allTypes.ts` 或 `schemas.py` 全系統單檔。
- 用 `Manager`、`Helper`、`Common`、`Misc`、`BaseService` 掩蓋無法說明的責任。

應以能搜尋的責任命名：

| 不可取 | 改為 |
|---|---|
| `utils.ts` 裡的 `format()` | `formatMoney.ts` 裡的 `formatMoney()` |
| `helpers.py` 裡的 `parse()` | `transforms/dates.py` 裡的 `parse_legacy_date()` |
| `types.ts` 裡的所有 UI 型別 | 各 feature 的 `customerUiModels.ts`、`shipmentUiModels.ts` |
| `CommonService.update()` | `confirm_shipment()` 或 `update_customer_contact()` |

小型、緊密相關的 types 優先與使用者同檔；當它們被多個檔案共用且有穩定邊界時，才移入有 domain 語意的專用檔。

## 13. 端到端範例

以建立客戶為例，名稱應連貫：

```text
React page                 CustomerCreatePage.tsx
React form                 CustomerForm.tsx
Zod schema                 customerFormSchema
UI form type               CustomerFormValues
generated request type     CustomerCreateRequest
API route                  POST /api/v1/customers
FastAPI handler            create_customer
application service        create_customer
Pydantic response          CustomerResponse
SQLAlchemy model           Customer
PostgreSQL table           customers
duplicate error code       CUSTOMER_CODE_ALREADY_EXISTS
backend test               test_create_customer_rejects_duplicate_code
frontend test              CustomerForm.test.tsx
```

以確認出貨為例，不將狀態轉換伪裝成通用 CRUD：

```text
React mutation hook        useConfirmShipmentMutation
API route                  POST /api/v1/shipments/{shipment_id}/confirm
request schema             ShipmentConfirmRequest
service                    confirm_shipment
error code                 SHIPMENT_INSUFFICIENT_STOCK
backend test               test_confirm_shipment_rejects_insufficient_stock
```

## 14. Review checklist

### 命名與邊界

- [ ] 新名稱使用已簽認 domain 語言，沒有 `misc`、`common`、`new`、`final2` 或不明縮寫。
- [ ] 檔案、class、函式、變數、常數與資料夾符合各語言命名格式。
- [ ] 每個檔案只有一個主要變更理由，沒有跨過 UI/API/service/DB 邊界。
- [ ] 超過拆檔門檻的程式碼已拆分，或在進度紀錄有可審核例外。
- [ ] 沒有新增萬用 `utils`、`helpers`、`types`、repository 或 base service。

### 前端與 UI

- [ ] 頁面使用 `frontend/src/ui/` 與 ADR-010 通用版型，沒有自創視覺。
- [ ] component、hook、schema、API query/mutation 與 view model 責任已分開。
- [ ] 新 UI 可跨模組時才進 `ui/`，且完成 RWD、鍵盤與狀態測試。
- [ ] OpenAPI types 沒有被手寫同名 DTO 取代。

### 後端、API 與資料庫

- [ ] Router 只負責 HTTP 邊界，service 負責 transaction 與業務規則。
- [ ] Route 、JSON、schema、錯誤碼與 SQL 命名可從 domain 語意相互對應。
- [ ] 狀態轉換使用明確 command，不是可任意改寫的 `update_status`。
- [ ] migration 單一、可還原且已測試 upgrade/downgrade。
- [ ] 新錯誤碼穩定、有 API 測試，且 UI 有可理解的處理。

### 測試、Import 與文件

- [ ] 測試名清楚表達條件、動作與結果，fixture 沒有正式客戶資料。
- [ ] Import reader、transform、mapping、apply、reconciliation 沒有混在同一函式或檔案。
- [ ] 新檔案已加入正確文件索引，README、進度紀錄與必要 ADR 已同步。
- [ ] lint、typecheck、unit/integration tests、UI 規範檢查、文件檢查與 `git diff --check` 通過。
